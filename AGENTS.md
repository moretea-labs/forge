# Forge AGENTS.md

## Development workflow (2026-11-11; current policy)

This root file is the sole repository-wide instruction authority. This policy replaces legacy Work/WorkHandle/Plan-driven execution instructions in prior versions of this file.

- **GitHub Issues and GitHub Project are the ONLY development progress ledger.** For every task, reuse the existing open Issue, record objective, priority, acceptance checklist, PR/commit/CI/test evidence, blockers and remaining steps there. Keep Issues **OPEN** until the user-authorized acceptance criteria have real, verifiable requirement-to-implementation evidence; close only after verifying those criteria, never automatically on code/PR merge. An independent reviewer is not a prerequisite. Use `Refs #123` in PR/commit text, never auto-close keywords. Do not create a second Issue, Requirement/Plan progress store, local TODO/progress database or parallel task record for the same goal. An explicitly requested optional Work is an execution resource, never a second task/progress ledger.
- **Work is explicit opt-in, never mandatory.** Normal development must not create, recover, or require Work/WorkHandle/Plan/Requirement, even when legacy Work exists. If the user explicitly selects Work, its existing isolated checkout, bounded verification, and resource cleanup may be used with Work-scoped identity and permissions; it must not become GitHub progress authority, own an extra Scheduler/liveness path, or veto ordinary Work-free repository operations. Do not auto-create Work from an Issue or resume historical Work without explicit ownership and effect reconciliation. Forge Process/Git leases and operation receipts remain the execution-safety owners; retired Supervisor Task/Effect history is read-only, never a live continuation owner. GitHub Issue + Project remains the only outcome/progress authority.
- **Single canonical integration line; checkout selection belongs to the user/model.** Use the current remote integration ref (`origin/main` unless the repository names another) as the shared source baseline; a local branch is not a second integration authority. Normally reuse the registered primary checkout, or the existing Issue branch and checkout when isolation is needed. Direct integration-branch development is appropriate only when the work can be legally delivered to the remote integration ref, the checkout is synchronized, and there is no competing writer or foreign dirty state. When branch protection requires a PR, the integration checkout is divergent, or concurrent writers require isolation, select one existing Issue branch (create one only if necessary) and start new source work from the current remote integration baseline. A branch is a Git history boundary, not a reason to allocate another directory. Forge reports facts and executes exact authorized actions; the model decides isolation and records owner, checkout, integration path and reason on the same Issue. Before changing branch/task inspect actual HEAD, dirty state, worktrees, unique commits and leases; never disturb another writer or unknown effect. Do not remove worktrees without clean, retained-source and unowned evidence.
- **Continuous integration and branch retirement.** Before delivery fetch and compare the actual remote integration ref and the selected source tip, and confirm ownership and leases. For an isolated branch, reconcile with the current remote baseline at a safe boundary (rebase only an owned branch when safe; otherwise use a normal non-destructive integration), review the cumulative diff, run the minimum relevant checks and use the repository-required protected PR or permitted fast-forward. For direct work, commit precisely owned validated changes and push legally to the remote integration line. A local commit or branch push is an intermediate receipt, not integration; verify the accepted change on the actual remote integration ref and update the same Issue. Never rebase or force-push shared main, a foreign active branch, or a dirty checkout. If integration is blocked, preserve all source and make reconciliation/required checks/PR the next actionable source delivery step for that lane; do not accumulate unrelated local main commits or spawn duplicate integration branches. Divergent main is a reconciliation source, not a base for new unrelated work. Compare ancestry, patch equivalence and current behavior before porting unique changes; retain valid upstream changes and foreign dirty paths. After remote integration, synchronize the local mirror and retained branches at safe owner boundaries; retire only verified clean, unowned, integrated/superseded branches and worktrees through supported cleanup. Never block unrelated disjoint work solely because another lane is integrating.
- **Direct Edit and terminal first.** Use existing Forge Direct Edit or authorized terminal `rg`, `git`, build/test commands for the shortest code-to-result path in the canonical checkout. Do not create orchestration for ordinary edits. Stage/commit precisely owned files and push/review only validated diff. Never overwrite unrelated dirty/untracked content.
- **Deliver validated increments end to end.** For each coherent source slice, review and commit exactly the validated owned paths, publish through the existing legal integration path, and verify the remote integration SHA/PR receipt before treating its source delivery as settled or moving to unrelated work on that lane. Record local commit, remote branch push, merged source, and installed/user-flow acceptance distinctly on the existing Issue. Product/live acceptance may remain OPEN after source integration; a pending build or CI can overlap genuinely independent work. Dirty state alone is not a commit blocker for disjoint owned paths, but a dirty/divergent shared checkout must not become a competing integration line. If a lease, check, permission or unresolved outcome blocks integration, record the exact blocker and resume the first safe integration action when it changes; do not substitute repeated local commits, status reports, or Runtime candidates for remote source delivery. Source integration never authorizes Runtime activation; existing safety contracts and Main gate remain intact.
- **Whole-system thinking and independent judgment.** Treat the prompt, issue checklist and reported symptom as entry points, not an exhaustive specification of what matters. Start from the actual user goal and end-to-end journey, observe the current product/system as a whole, and form an independent mental model of relevant users, domain rules, information architecture, interactions, shared components, data/ownership boundaries, dependencies and failure paths. Compare the desired experience with actual behavior; actively look for material unreported omissions, conflicts, regressions and better product or technical choices, including whether the requested local fix is the right solution. Move deliberately between whole, part and whole: identify the highest-value coherent outcome, trace underlying relationships before editing, implement the smallest sufficient change (including necessary adjacent changes within authorization), then review the integrated result in context. Do not merely satisfy literal wording or optimize isolated metrics; do not mistake holistic reasoning for reading the entire repository, expanding scope without value, inventing requirements, or overriding explicit product decisions and safety boundaries. Reuse established context and evidence, and broaden investigation only where it can change the decision or outcome.
- **Proactive problem discovery and continuous improvement.** The model owns both the requested user outcome and the quality of the method used to deliver it. While understanding, designing, implementing, validating and executing tools, compare actual results with expectations and actively identify product/design regressions, recurring defects, wasted work, excessive complexity, unreliable tooling and disproportionate constraints. Investigate the observed evidence, original purpose, common root cause, current necessity, alternatives and impact; do not assume an existing rule is correct or that a tool defect is proven. Within existing authorization, correct a high-value root cause at its canonical owner and validate the actual improvement rather than repeatedly retrying, reporting a blockage or bypassing it. Preserve legitimate safety objectives and authorization; improve their implementation, never evade them. Keep the main user outcome primary, choose the smallest sufficient change and defer speculative or unrelated optimization. Reuse validated evidence and record reusable semantic lessons or explicit user corrections in the existing Cognitive Plane and applicable guidance, not in a separate process, reviewer, gate or knowledge store. Success means better user outcomes, fewer repeated failures and less wasted delivery effort, not more activity or reflection reports.
- **Model-directed progressive evidence gathering.** The user/model owns the investigation hypothesis, query selection, which gaps matter, next retrieval step and stopping decision; Forge is a bounded read/execute mechanism, not a planner, recommender or semantic completeness authority. `rh_context` may mechanically rank/expand source candidates and return provenance, truncation, omissions, denied paths and readiness diagnostics, but those are evidence, not an instruction, workflow gate, automatic follow-up job or permission to stop. Before implementation, trace the observed behavior/expected outcome through materially relevant entry points, callers/callees, shared state/persistence, config, async/error paths, cross-module contracts, tests, docs and recent changes. When the entry is unknown start broad; after every result the model checks new leads and evidence gaps, then explicitly calls targeted `rh_context`/`rg`/file reads/semantic references as needed. Read material omitted/truncated/unmaterialized paths rather than assuming the first search was complete. Reconcile evidence with a reproduction or falsifiable root-cause hypothesis and impacted callers before editing. Stop when the significant paths and risks are explained, not after a fixed number of rounds or a tool-provided confidence flag. Do not require whole-repo reading, extra agents, parallel retrieval authorities or Forge-generated recommendations. Report inaccessible material paths and remaining uncertainty.
- **Repeatable issue queue:** inspect the repository's OPEN Issues and GitHub Project; take the highest priority *actionable* item within the user's current scope; read actual source and latest PR/CI; execute a meaningful change/check/review/integration; update its Issue/Project with evidence, blockers and next action; immediately proceed to the next actionable item. Revisit blocked items only when material evidence or dependency changes. Do not equate a repeated status report/CONTINUE with throughput; do not poll without new evidence.
- **Non-blocking long-running work:** a started CI run, managed Process, build/test, remote merge, provider job, or other long operation is **not** a reason to block the conversation when its result is not yet a dependency. Record its stable identity/receipt, continue other independent actionable work, and join/read it only when its result is required for the next effect, integration decision, or final acceptance. The existing process_wait attachment is capped at 5 seconds; unregistered workspace_root direct commands are capped at 30 seconds and do not return a durable Process handle, so longer operations must use registered checkouts. At most one bounded attachment is appropriate at a true dependency boundary; if it is still running, continue independent work, or if none remains, report its exact Process/Job handle and pending acceptance and then end the ChatGPT response rather than holding the turn in 'thinking'. Do not loop on `process_wait`, status reads, sleeps, or equivalent polling. A single bounded join/read is the default; after outcome-unknown external effects, reconcile once with authoritative read-only state before deciding whether a retry is safe.
- **Task-bound continuation (#313):** Launch Session remains Work-free and may send one explicit Prompt only when an existing `task_id` is supplied. Reuse that task's exact active ChatGPT conversation and browser tab. Create a replacement only after read-only evidence proves the original session missing or the conversation unusable; the replacement must recover the latest Issue/progress/confirmed deliveries and bind back to the same task. Commit takeover only after an applied Send receipt and canonical conversation URL are proven. Outcome-unknown Sends block replacement/replay. Archive predecessor lineage and close its exact Forge-owned tab only after takeover; retry cleanup with the same request identity until one active task → one conversation → one tab is restored. Do not restore Work-bound Supervisor Task/Turn, ControllerRound, a second scheduler, duplicate task ledger, watcher-inferred DONE, or blind provider retry.
- **Safety contracts persist:** scoped authorization and strong confirmation, Git SHA/CAS/checkout/path/ref leases, secret isolation, exactly-once external writes, non-overlapping source ownership, release/recovery approvals and rollback evidence. Unknown/applied external Sends cannot be blindly resent. A legacy gate that still enforces Work is a defect for #483 to fix, not permission to bypass the real authorization/Git/effect authority through another tool.
- **Avoid redundant approval prompts:** Check effective access and existing grants before asking the user. In `full_access`, proceed with ordinary repository and permitted host reads, scoped edits, checks and Git operations under the host permission model; do not invent an additional Forge approval. For read-only external filesystem diagnostics, reuse an active narrow target; when the user has expressly approved the exact paths and purpose for the current task, apply the required preview ticket and reuse that grant without another chat confirmation. Keep the grant path-bounded and time-bounded. `full_access` and prior grants do not override protected secrets, OS privacy controls, destructive changes, external-effect replay, Runtime activation or publication authorization.
- **Mac canonical Forge source:** no competing WSL Writer. Release/source switch, restart, rollback or cutover is separate from code development and is not authorized by changing instructions.

## UI implementation quality — acceptance for every UI task

Building successfully, seeing elements in the tree, and passing outer-rectangle overlap checks do NOT constitute UI acceptance. The current executor verifies the real UI; do not create an independent Reviewer, a second provider, gate daemon, task ledger or compatibility path. Apply to Forge Client and all app, web, extension, simulator and native UI tasks that Forge executes.

- **Design from a proven baseline, not the technology or the latest draft.** For an existing product, identify the actual accepted/released reference version and inspect the relevant whole screens, adjacent destinations, shared components and end-to-end journey before changing them. Establish what already works and must remain (information hierarchy, geometry, optical weight, material, navigation, feedback), what user value requires change, and why the chosen design improves it. The latest intermediate implementation is not a quality baseline; do not replace a good design merely to use a newer API, Glass, a new platform or to make it look different. Preserve established choices unless a demonstrable improvement or real compatibility need justifies change; restore proven visual behavior without rolling back unrelated functionality when a regression occurs. For new products use the agreed design/reference and actual user goal; never invent a previous baseline.
- **Challenge the problem framing and inherited design assumptions.** For material information-architecture or interaction changes, independently derive the actual user jobs, frequency (distinguish observed facts from assumptions), decision needs, navigation/action/content responsibilities and measurable improvement over the unchanged baseline. Ask whether existing titles, tabs, cards, actions and hierarchy are necessary, can be removed, combined, relocated, disclosed contextually, or replaced by a different interaction paradigm. Explore meaningfully different structures, including retaining the existing design, rather than cosmetic rearrangements or merely reflecting the user's suggested implementation. Preserve important discoverability, domain meaning, safety and accessibility; never optimize a local metric at the expense of the whole task. For small clear corrections use the direct fix, not mandatory alternative counts or a new design phase.
- **Actively falsify proposed designs before choosing them.** For each serious candidate, including your preferred one, walk through the actual high-value tasks and adverse states; seek concrete reasons it would fail, compare against the baseline, and distinguish unresolved assumptions from verified behavior. Account for the entire space budget (including sticky/floating controls, scroll clearance, keyboard, safe areas and density of content), action discoverability and extra steps, one-handed reach and gesture conflicts, localization, adaptive/accessibility layouts, empty/few/many/complex items, visual balance, platform conventions and domain errors. Reject or revise materially worse candidates; do not hide known disadvantages behind scores, aesthetics, mockups or unsupported claims. Select the smallest coherent design only after identifying the trade-offs, mitigation and remaining evidence that could overturn the decision. For uncertain consequential choices use a bounded prototype and real comparative interaction, not premature production changes, mandatory design gates or extra reviewers. Verify the selected hypothesis in the existing acceptance workflow and revisit it if evidence contradicts it.
- **Model final composition before implementation.** Work whole page → region → component → internal layout → integrated page. Trace who owns each dimension, alignment, content inset, background/material, safe-area inset and navigation/scroll placement, including containers and platform styles that add their own sizing or decoration. Distinguish glyph/text optical bounds, visible surface, label proposal and interactive/accessibility hit area; a 44pt minimum hit target is not an instruction to enlarge a rendered icon or set a 44pt inner label inside another padded control. Use exactly one effective owner for each visible container/inset; prefer existing tokens and native behavior where they preserve the design, avoid nested chrome and compensation offsets. Specify expected final sizes and reasonable upper/lower bounds, internal horizontal/vertical padding, optical center/baseline, spacing and relationships to neighboring controls, not just minimum size or a component in isolation. Review default and adaptive layouts without forcing all controls into one fixed dimension.
- **Compare rendered outcomes, not intentions.** For modifications compare the same device/viewport, language, text size, data state and interaction with the proven baseline, using exact source/build identity; reuse matching reference evidence. Inspect the full screen and affected neighboring screens, including screens sharing any changed component; verify intended improvements and unchanged visual/behavior invariants. Check final outer and inner geometry, visual hierarchy, background continuity, safe-area/scroll transitions and native feedback, not merely AX minimums or screenshot generation. For adaptation, preserve the standard device experience and verify the genuinely affected alternate viewport. Reject a demonstrably worse design even if tests pass; use focused measurable regression assertions where meaningful, not an additional gate or universal pixel thresholds. If reference/rendering is unavailable identify the evidence gap explicitly, do not claim equivalence or approval.
- Static design first, real rendering next. Check the actual screen and content hierarchy before launching costly simulators; then inspect the actual app/page (DOM geometry and computed styles plus screenshot for web; accessible element frames plus screenshot/device interaction for native). Do not transfer Web-only evidence to a native app, or claim PASS where the real renderer was unavailable.
- Alignment and spacing: measure repeated left/right baselines, row spacing, typography baselines, button-label/icon centers, section gaps, form alignment and content-to-edge padding. For intended same-column controls use <=2px x/width variation; for label/control alignment <=5px centerline difference, unless a documented platform-native metric justifies another bound. Check text/icon/caret clearance inside controls, not only outer rectangles: a designed dropdown caret needs >=12px edge inset and >=8px additional text clearance. Avoid universal fixed card heights or treating equal spacing everywhere as correct.
- Coverage: inspect default and long Chinese/English text, empty/few/many items, narrow/short and standard screen sizes, dynamic text/accessibility where relevant, active/disabled/loading/selected/error states, focus/keyboard, scrolling, menus/sheets/popovers/dialogs, safe areas and toolbar/tab-bar interaction. Check overflow, unintended wrapping, clipped labels, hidden primary actions, card collisions, unreachable content and excessive blank space. Sparse content should have deliberate visual balance; expansion should be natural.
- Visual restraint: prefer layout, font hierarchy, whitespace and contrast instead of stacked backgrounds, redundant cards, conspicuous borders, shadows and gradients; retain only separators, focus rings, selection treatments and containers with identifiable function. Current executor reviews real screenshot and interactions; measured geometry PASS is necessary but does not prove visual quality.
- Verification outcome: for a regression first reproduce a failing visual/geometry/interaction assertion, then fix common root cause and verify against the same fixture. Reuse unchanged source-fingerprint, viewport/device and test receipts; do not rerun identical expensive checks. Record exact viewport, dimensions, observed defects, screenshot and outcome in the existing GitHub Issue as PASS / FAIL / NOT RUN / BLOCKED. Do not label UI ready if a critical known overlap, clipping, alignment, spacing or interaction defect remains. Never weaken acceptance tests or hide errors to get green.

## Execution / acceptance
1. The user/model selects the checkout and investigation strategy; Forge returns factual checkout/source evidence and executes the requested operations. Read the current Issue goal, observable behavior, current checkout/diff, real code and constraints; iterate model-chosen source queries until the cause and affected paths are evidence-supported (or document the unresolved gap); then identify the smallest coherent change.
2. Edit via Direct Edit or terminal; for regressions reproduce the defect, implement the minimum fix and use focused tests with actual behavior evidence.
3. Review the exact cumulative diff as the current executor, select the minimum sufficient behavior tests and CI for the change risk, and resolve known defects. Independent model/human review is optional and does not block commit, PR integration or Issue completion unless the user expressly requests it or an existing repository branch-protection rule enforces it. Never weaken actual tests, authorization or release safety checks to remove a review dependency.
4. Deliver through Git with exact SHA and legal integration; record receipts, acceptance gaps and next steps on the SAME GitHub Issue/Project. Leave Issue OPEN.
5. Continue the next actionable Issue. When blocked by user authorization, unavailable provider or external CI, record a precise blocker and stop spinning until the real trigger.

## Architecture

- Thin, decoupled, single authority/owner/writer/path for every durable fact. Fix the violated invariant and migrate all callers; delete obsolete fallback, compatibility layers, redundant state, legacy lifecycle gates, and tests in the same coherent change where safe.
- Forge is one whole Runtime with one lifecycle/recovery authority; Gateway, Scheduler, Controller and transports are modules, not competing deployable processes. Do not introduce another daemon, watchdog, retry loop, Provider, status state machine, or control plane without a real independent boundary.
- Keep Kernel/domain public port/API boundaries and repository module/import rules: `docs/architecture/CURRENT.md`. For migrations inspect all direct/indirect callers and relevant docs/tests before claiming old-path retirement.
- Browser/ChatGPT generation state from DOM/Stop/stable text is not a provider completion receipt. Require exact operation identity and trusted completion/failure evidence for authorized external actions. Legacy Supervisor Task/Effect/Turn receipts remain historical; unknown/applied effects are never replayed. Respect Retry-After; repeated unknown observations are not productive progress.
- Preserve staged/unstaged/untracked data and unique Git commits. No silent clean/reset/stash/force rebase, shared file overwrite, credentials in code, unauthorised production release or false DONE.
- UI changes require rendered interaction review; backend/Runtime changes require relevant real behavior evidence. Old failing tests can be removed only after their contracts are genuinely retired; run a focused RED→GREEN regression for current defects.
- Historical Forge Work/Plan/Requirement data may exist but is not a current progress ledger or ordinary operation prerequisite.
