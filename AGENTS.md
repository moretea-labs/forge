# Forge AGENTS.md

## Development workflow (2026-11-04; current policy)

This root file is the sole repository-wide instruction authority. This policy replaces legacy Work/WorkHandle/Plan-driven execution instructions in prior versions of this file.

- **GitHub Issues and GitHub Project are the ONLY development progress ledger.** For every task, reuse the existing open Issue, record objective, priority, acceptance checklist, PR/commit/CI/test evidence, blockers and remaining steps there. Keep Issues **OPEN** until the user-authorized acceptance criteria have real, verifiable requirement-to-implementation evidence; close only after verifying those criteria, never automatically on code/PR merge. An independent reviewer is not a prerequisite. Use `Refs #123` in PR/commit text, never auto-close keywords. Do not create a second Issue, Requirement/Plan progress store, local TODO/progress database or parallel task record for the same goal. An explicitly requested optional Work is an execution resource, never a second task/progress ledger.
- **Work is explicit opt-in, never mandatory.** Normal development must not create, recover, or require Work/WorkHandle/Plan/Requirement, even when legacy Work exists. If the user explicitly selects Work, its existing isolated checkout, bounded verification, and resource cleanup may be used with Work-scoped identity and permissions; it must not become GitHub progress authority, own an extra Scheduler/liveness path, or veto ordinary Work-free repository operations. Do not auto-create Work from an Issue or resume historical Work without explicit ownership and effect reconciliation. Forge Process/Git leases and operation receipts remain the execution-safety owners; retired Supervisor Task/Effect history is read-only, never a live continuation owner. GitHub Issue + Project remains the only outcome/progress authority.
- **Single canonical workspace by default; selection belongs to the user/model.** For each repository normally use its existing registered primary checkout and at most one active source Writer. A user may explicitly select a worktree, or the model may choose one after establishing a concrete isolation need; Forge must neither recommend nor autonomously select/create/switch worktrees from an Issue, Work, task, dirty state, or default heuristic. Forge executes the caller's exact authorized checkout/Git action and reports facts, conflicts and safety constraints, not a preferred workflow. For ordinary Issue work prefer the canonical checkout; one Issue should have at most one development branch. A branch is a Git history boundary, not a reason to allocate another directory. Before changing branch or task, inspect current HEAD, worktree list, tracked/untracked edits, unique commits, and execution/ref leases; never reset/stash/overwrite another task's state to force a single checkout. When the model or user selects isolation, record the actual reason, checkout identity, owner, integration/cleanup path on the same Issue, and preserve existing branch/lease safety. Do not remove existing worktrees without evidence of clean state, unique-commit retention and no active ownership.
- **Rebase-first integration and branch retirement.** For every Forge-managed repository, retain one canonical integration line (`main` unless the repository names another) and normally one development branch per Issue. Before delivery, fetch and compare the exact integration HEAD, confirm ownership/leases and a clean worktree, then rebase the owned feature branch onto the current integration branch; verify its cumulative diff and focused checks, integrate by fast-forward where permitted (otherwise use the repository's required protected-branch PR), and record the resulting SHA on the existing Issue/Project. Never rebase or force-push shared `main`, an active foreign branch, or a dirty checkout. If commits are no longer in ancestry, check patch equivalence AND current behavior before deciding whether to port any still-valid delta; do not blindly replay superseded historical Work or restore retired architecture. After integration, remove only confirmed clean, unowned, fully integrated/superseded branches and worktrees through supported Git/Forge cleanup; preserve unresolved diffs, unique commits, dirty files and Recovery snapshots with exact owner/evidence until reconciled. New work starts from the freshly updated canonical integration HEAD, not a stale feature/worktree head.
- **Direct Edit and terminal first.** Use existing Forge Direct Edit or authorized terminal `rg`, `git`, build/test commands for the shortest code-to-result path in the canonical checkout. Do not create orchestration for ordinary edits. Stage/commit precisely owned files and push/review only validated diff. Never overwrite unrelated dirty/untracked content.
- **Model-directed progressive evidence gathering.** The user/model owns the investigation hypothesis, query selection, which gaps matter, next retrieval step and stopping decision; Forge is a bounded read/execute mechanism, not a planner, recommender or semantic completeness authority. `rh_context` may mechanically rank/expand source candidates and return provenance, truncation, omissions, denied paths and readiness diagnostics, but those are evidence, not an instruction, workflow gate, automatic follow-up job or permission to stop. Before implementation, trace the observed behavior/expected outcome through materially relevant entry points, callers/callees, shared state/persistence, config, async/error paths, cross-module contracts, tests, docs and recent changes. When the entry is unknown start broad; after every result the model checks new leads and evidence gaps, then explicitly calls targeted `rh_context`/`rg`/file reads/semantic references as needed. Read material omitted/truncated/unmaterialized paths rather than assuming the first search was complete. Reconcile evidence with a reproduction or falsifiable root-cause hypothesis and impacted callers before editing. Stop when the significant paths and risks are explained, not after a fixed number of rounds or a tool-provided confidence flag. Do not require whole-repo reading, extra agents, parallel retrieval authorities or Forge-generated recommendations. Report inaccessible material paths and remaining uncertainty.
- **Repeatable issue queue:** inspect the repository's OPEN Issues and GitHub Project; take the highest priority *actionable* item within the user's current scope; read actual source and latest PR/CI; execute a meaningful change/check/review/integration; update its Issue/Project with evidence, blockers and next action; immediately proceed to the next actionable item. Revisit blocked items only when material evidence or dependency changes. Do not equate a repeated status report/CONTINUE with throughput; do not poll without new evidence.
- **Non-blocking long-running work:** a started CI run, managed Process, build/test, remote merge, provider job, or other long operation is **not** a reason to block the conversation when its result is not yet a dependency. Record its stable identity/receipt, continue other independent actionable work, and join/read it only when its result is required for the next effect, integration decision, or final acceptance. The existing process_wait attachment is capped at 5 seconds; unregistered workspace_root direct commands are capped at 30 seconds and do not return a durable Process handle, so longer operations must use registered checkouts. At most one bounded attachment is appropriate at a true dependency boundary; if it is still running, continue independent work, or if none remains, report its exact Process/Job handle and pending acceptance and then end the ChatGPT response rather than holding the turn in 'thinking'. Do not loop on `process_wait`, status reads, sleeps, or equivalent polling. A single bounded join/read is the default; after outcome-unknown external effects, reconcile once with authoritative read-only state before deciding whether a retry is safe.
- **Retired autonomous continuation (#313):** Launch Session is a one-shot, Work-free open/bind operation and never sends a model prompt or `CONTINUE`. Independent Schedule executes one explicitly authorized action per occurrence with its own receipt; legacy `external_controller_wake` / `controller_progression` actions remain disabled and fail closed. Do not restore Supervisor Task/Effect/Turn, watcher-triggered model wake, automatic retry/recover, or a parallel native host. Keep historical audit read-only and never replay unknown/applied external effects. Continue development from GitHub Issue/Project and current Git evidence through an explicitly launched session, without duplicate Writers or mandatory independent Review.
- **Safety contracts persist:** scoped authorization and strong confirmation, Git SHA/CAS/checkout/path/ref leases, secret isolation, exactly-once external writes, non-overlapping source ownership, release/recovery approvals and rollback evidence. Unknown/applied external Sends cannot be blindly resent. A legacy gate that still enforces Work is a defect for #483 to fix, not permission to bypass the real authorization/Git/effect authority through another tool.
- **Avoid redundant approval prompts:** Check effective access and existing grants before asking the user. In `full_access`, proceed with ordinary repository and permitted host reads, scoped edits, checks and Git operations under the host permission model; do not invent an additional Forge approval. For read-only external filesystem diagnostics, reuse an active narrow target; when the user has expressly approved the exact paths and purpose for the current task, apply the required preview ticket and reuse that grant without another chat confirmation. Keep the grant path-bounded and time-bounded. `full_access` and prior grants do not override protected secrets, OS privacy controls, destructive changes, external-effect replay, Runtime activation or publication authorization.
- **Mac canonical Forge source:** no competing WSL Writer. Release/source switch, restart, rollback or cutover is separate from code development and is not authorized by changing instructions.

## Execution / acceptance

1. The user/model selects the checkout and investigation strategy; Forge returns factual checkout/source evidence and executes the requested operations. Read the current Issue goal, observable behavior, current checkout/diff, real code and constraints; iterate model-chosen source queries until the cause and affected paths are evidence-supported (or document the unresolved gap); then identify the smallest coherent change.
2. Edit via Direct Edit or terminal; for regressions reproduce the defect, implement the minimum fix and use focused tests with actual behavior evidence.
3. Review the exact cumulative diff as the current executor, select the minimum sufficient behavior tests and CI for the change risk, and resolve known defects. Independent model/human review is optional and does not block commit, PR integration or Issue completion unless the user expressly requests it or an existing repository branch-protection rule enforces it. Never weaken actual tests, authorization or release safety checks to remove a review dependency.
4. Deliver through Git with exact SHA and legal integration; record receipts, acceptance gaps and next steps on the SAME GitHub Issue/Project. Leave Issue OPEN.
5. Continue the next actionable Issue. When blocked by user authorization, unavailable provider or external CI, record a precise blocker and stop spinning until the real trigger.

## Architecture

- Thin, decoupled, single authority/owner/writer/path for every durable fact. Fix the violated invariant and migrate all callers; delete obsolete fallback, compatibility layers, redundant state, legacy lifecycle gates, and tests in the same coherent change where safe.
- Forge is one whole Runtime with one lifecycle/recovery authority; Gateway, Scheduler, Controller and transports are modules, not competing deployable processes. Do not introduce another daemon, watchdog, retry loop, Provider, status state machine, or control plane without a real independent boundary.
- Keep Kernel/domain public port/API boundaries and repository module/import rules: `docs/architecture/CURRENT.md`. For migrations inspect all direct/indirect callers and relevant docs/tests before claiming old-path retirement.
- Browser/ChatGPT generation state from DOM/Stop/stable text is not a provider completion receipt. Require exact operation identity and trusted completion/failure evidence for authorized external actions. Legacy Supervisor Task/Effect/Turn receipts remain historical; unknown/applied effects are never replayed. Respect Retry-After; repeated unknown observations are not productive progress.
- Preserve staged/unstaged/untracked data and unique Git commits. No silent clean/reset/stash/force rebase, shared file overwrite, credentials in code, unauthorised production release or false DONE.
- UI changes require rendered interaction review; backend/Runtime changes require relevant real behavior evidence. Old failing tests can be removed only after their contracts are genuinely retired; run a focused RED→GREEN regression for current defects.
- Historical Forge Work/Plan/Requirement data may exist but is not a current progress ledger or ordinary operation prerequisite.
