# 让多个项目会话并发执行时保持正确和稳定

修复多项目、多会话并发下的上下文串源、共享 Gateway 被重任务拖垮、Direct Edit 绕过调度写隔离、同步锁阻塞事件循环、编译运行时诊断入口失效和耗时不可归因问题。先保证显式 repo/checkout 身份和同 checkout 单写者正确性，再隔离重执行负载，最后依据端到端分阶段遥测调整并发容量。

## Goals

- 显式 repo_id + checkout_id 的任何读取都只能返回该 checkout 当前身份对应的投影，缓存不一致时 fail closed。
- Gateway 只承担有界路由、状态读取和任务受理，Git 扫描、诊断、基准、检查和投影重建运行在独立 Process/Worker 中。
- 所有写入路径，包括 Direct Edit，都纳入统一的 repository/checkout/work/path claim；同 checkout 默认单写者，跨仓库和独立 worktree 可并行。
- 锁等待不阻塞 Gateway 事件循环，关键区保持有界，并能观察 lock wait、queue wait 和 resource pressure。
- 编译发布后的 watchdog、maintenance 和性能诊断入口可独立运行并返回一致终态。
- 每个 Work/Process 持久化阶段耗时，使 p50/p95、失败重试浪费、Gateway 中断和收尾成本可量化。

## Non-goals

- 不通过简单提高 MAX_WORKERS 掩盖隔离和一致性缺陷。
- 不允许多个会话直接并发修改同一 canonical checkout。
- 不把完整测试、Git 扫描或长诊断重新塞进 Gateway 请求线程。
- 不重置、stash、覆盖或代提交当前主工作区中的其他会话修改。
- 不执行远程 push、发布或运行时切换。

## Acceptance Criteria

- [ ] 100 次跨会话并发显式 checkout 读取均返回一致 repoId、checkoutId、root、branch、HEAD 和 projection source identity，旧 refresh 不得覆盖新 generation。
- [ ] 一个项目运行长检查或诊断时，其他三个项目的有界状态读取保持可用，Gateway 不因该负载触发 readiness restart。
- [ ] 同 checkout 第二个 writer 被排队或明确拒绝；不同仓库和不同受控 worktree 在资源允许时可并发。
- [ ] Gateway 请求路径不存在 Atomics.wait 或其他同步轮询锁等待；锁冲突有结构化指标。
- [ ] watchdog、runtime maintenance 和性能诊断在编译发布目录中通过 focused tests，不再把 Bun executable path 当子命令。
- [ ] 遥测能分解 identity、routing、cache、lock、worktree、queue、startup、execution、verification、integration、cleanup、projection、serialization 和 restart interruption。
- [ ] 在正确性门禁通过后执行 1/2/4/8 仓库压测，并根据资源压力结果确定默认并发，不预设提高当前 4 Worker。
