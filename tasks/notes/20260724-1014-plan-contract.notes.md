## Design Decisions

- PlanContract is a separate controller metadata store, intentionally not a WorkContract field. This preserves WorkContract as the execution/workspace/worker lifecycle owner and avoids a second execution state machine.
- Plan operations remain `rh_work` suboperations. Adding `rh_plan` would enlarge the default facade exactly where the proposal identified discovery-cost pressure.
- Scope conflict is enforced at approval only for approved-or-later nonterminal plans, so competing drafts can be reviewed without locking each other out.
- ExecutionJob is the durable authority for an execution attempt. Managed Process Runtime remains a subordinate process/command substrate with operational telemetry, not a competing Job or Scheduler.
- Complex `rh_work.start` now requires an approved `plan_id + plan_step_id`, compares the Plan's frozen revision to live HEAD before a WorkContract exists, claims the step under a durable lock, and writes Plan provenance into the WorkContract. Finalization advances the step; acceptance failure routes the Plan to `replanning`.

## Tradeoffs Considered

| Option | Decision | Reason |
|--------|----------|--------|
| Separate PlanContract store | Selected | The existing WorkContract begins at execution and cannot truthfully represent pre-execution exploration or frozen assumptions. |
| Add a top-level `rh_plan` tool | Rejected | The default facade remains intentionally compact; suboperations preserve the five-tool boundary. |
| Require all existing `rh_work.start` calls to have a plan | Deferred | Dispatch has no durable `planId + stepId` binding yet; enforcing it now would block current workflows without a truthful execution linkage. |
