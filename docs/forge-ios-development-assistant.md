# Forge iOS Development Capability

Forge provides optional iOS simulator, physical-device, build, inspection, and App Store related operations through first-party adapters. Operations remain repository-scoped, permission-gated, timeout-bounded, and evidence-producing. Device or account approval remains a human interaction boundary. On a paired real iPhone, Computer rejects known-disconnected CoreDevice devices and unknown lock-state schemas before app activation. CoreDevice launch success is confirmed from valid structured JSON (not the human-readable stderr progress line), and app foreground is independently verified by a fresh screenshot before input. Structured subprocess JSON must remain parseable after secret redaction (including CoreDevice `auditToken`). Foreground-unconfirmed system navigation uses one-shot screenshot-bound `physical_device_observed_tap` or `physical_device_observed_swipe` to reach the target app; ordinary app gestures still require fresh verified target foreground. Fast physical-device tap/type requires the Controller-owned `pymobiledevice3 11.24.0` toolchain. Provision exactly `ControllerHome/toolchains/pymobiledevice3-11.24.0/bin/python` through the single repository installer `scripts/install-ios-hid-toolchain.sh <ControllerHome>` **only after** the ForgeInstance host `process:exec` grant is available. Provisioning does not authorize a Runtime switch or any phone input. The toolchain probe verifies the installed package version and required CoreDevice exports; a wrong-version executable fails closed before HID dispatch. Ordinary Computer Browser/Desktop manifest reads never launch Python to probe HID: they report only the sole provider's previously verified, short-lived readiness cache, while an explicit HID operation performs the strict probe. An `inputReady=false` manifest reading with an empty or stale cache is reported as unverified with an explicit "does not indicate a missing toolchain" warning; it never fabricates a toolchain failure reason, and the passive status exposes `probeState` (`verified-recent` / `probe-failed` / `unverified`) instead (#289). Version `10.2.1` incorrectly numbers successive RemoteXPC requests, causing the device-side connection to close during clipboard-backed Unicode input. A managed input action waits for its own worker initialization because prewarm from a prior isolated plugin process is not persistent authority. If that toolchain is not installed, the provider must report unavailable rather than claim live product prices. Shopping price claims require a fresh observed product or checkout view and its exact package specification; search listings or historical deal pages alone are not checkout evidence. CoreDevice screenshots are captured into a private per-session `0700` directory, then restricted to `0600` before being returned. A new capture first invalidates prior screenshot/foreground observations; failed or malformed captures remove partial artifacts. Only then do bounded PNG chunk framing, per-chunk CRCs, IHDR dimensions, image data and a terminal IEND qualify for a fresh observation ID, accompanied by byte count and SHA-256; these are byte-integrity facts, not proof of SKU, price or app foreground.

See [Plugin management](forge-plugin-management.md), [Human Interaction Plane](architecture/CURRENT.md), and the [iOS physical-device migration baseline](architecture/decisions/20260904-ios-device-migration-baseline.md).

Ordinary physical-iPhone App operation is exposed only under `plugin_id=computer`, using the existing `physical_device_*` action schemas and CoreDevice/RemoteXPC implementation, including exact-phone authorization and screenshot-bound input. The Computer manifest reports `health.details.iphone.observationReady` (CoreDevice screenshot) separately from `health.details.iphone.inputReady` (pinned Controller-owned HID Python); the former never implies the latter. The `ios` plugin retains Xcode build, Simulator, smoke review and explicit agent-device/XCTest development capabilities. No separate iPhone Computer provider, session store or implicit retry path is introduced. The new runtime-facing action surface requires a subsequent release activation and live phone acceptance before treating shopping or medical-document outcomes as verified.

For everyday App actions, screenshot freshness and an `observation_id` **do not** establish which App is currently foreground. The model must inspect the actual latest screenshot **before** confirming the exact target App and dispatching any coordinate or text mutation. Do not capture a new, unseen screenshot inside an automatic script and immediately use its observation ID for a prior screenshot's coordinates: the user can switch Apps between observations. Once the exact App is visibly established, use `physical_device_confirm_foreground` followed by the regular `physical_device_batch`, `physical_device_tap`, or `physical_device_type_text` path. A bare `observation_id` in `physical_device_batch` is never an authorization shortcut; even the fused screenshot-batch path requires independent explicit foreground confirmation. Reserve `physical_device_observed_tap` for independently inspected system navigation, and stop/re-observe if the screen belongs to another App. The source-only `scripts/smoke-ios-physical-device.ts` rejects disconnected/screenshot-unavailable iPhones before app inspection and includes the exact private screenshot path, SHA-256, byte count and observation ID after independently matching the provider's receipt. It explicitly reports `semanticPriceVerified: false`: this is source open/capture evidence, not a checkout-price comparison or an activated Runtime/MCP acceptance receipt; one-shot source acceptance must not prewarm a retained HID worker; a source process that does launch one must explicitly stop it before exiting.

## Private iPhone document access

Computer exposes `physical_device_documents_list` and `physical_device_document_export` through the existing exact iPhone/App CoreDevice session. Each requires a separate interactive strong confirmation: `list-iphone-app-documents` or `export-iphone-app-document`. The request must explicitly name the app `bundle_id`, which is checked against the exact owned interaction before any file access. Discovery is restricted to at most 100 PDF/image filenames from the selected app's `appDataContainer/Documents`. Export accepts one file directly under `Documents/`, copies it to a private Controller artifact (0700 folder, 0600 file), verifies regular-file type and bounded size (20 MiB), then checks PDF EOF framing, the existing PNG chunk/CRC parser, JPEG end-of-image, or HEIC initial file-type box bounds before returning size and SHA-256. These checks reject common truncated copies but do not prove that every PDF or image fully decodes. In the same private folder, the sole export writer atomically maintains a private (0600 from temporary-file creation through rename), bounded chronological `index.json` (up to 500 entries) with app identity, source relative path, artifact filename, time, size and checksum. Before any subsequent device copy, the existing index must be a regular file no larger than 512 KiB, belong to the exact current app and interaction, and contain only structurally valid entries; corrupt, foreign, full or oversized indexes fail closed without overwriting prior receipts. This organizes verifiable export facts only and does not interpret medical contents. There is no recursive, Files, iCloud, other-app, hospital-cloud or bulk scan, and no upload or device modification. Unsupported CoreDevice response schemas, including nonempty file lists with unrecognizable row names, fail closed rather than being reported as an empty directory. CoreDevice list-command failures redact raw stdout, stderr and command arguments to avoid disclosing private document names in error receipts. Neither capability is a receipt for an actual document until a separate consent and live device result are obtained.
