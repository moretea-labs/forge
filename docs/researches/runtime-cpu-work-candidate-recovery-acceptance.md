# Work candidate CPU and explicit Recovery acceptance

## Evidence and decision (2026-09-12)

Runtime release `1789203347359-260ddf6c…`, authority revision 320, was observed at 108.8% CPU (one core = 100%). Forge had 749 Work rows, 748 terminal, approximately 13.5 MB of JSON. The JSON-exclusion query returned one row but scanned historical payloads and used temporary ordering. An in-memory copy measured median 23.983 ms before and 0.011 ms with a matching partial index (15 iterations). This establishes query cost, not whole-Runtime acceptance. A governed revalidation on a SQLite backup of the current Controller Home observed 750 Work rows (364 cancelled, 360 completed, 25 failed, 1 running): the production-shaped candidate query was median 8.791 ms / p95 12.022 ms and required a temporary B-tree before the derived partial index, versus median 0.005875 ms / p95 0.006583 ms after the index, with the planner selecting the candidate index directly and returning one candidate. The backup-only benchmark did not mutate live authority.

This consolidates the performance defect in `8193effd`'s unindexed prefilter and the existing Recovery auto-attestation/explicit-rollback defect. No new incident-specific service, status authority, scheduler or cache is introduced.

## Ownership and closure

- Work owns namespace, status semantics, terminal exclusions and conservative candidate normalization. SQLite owns the physical, derived partial index. Runtime composition calls Work initialization during its existing database startup stage, before hot readers/scheduler start. Queries never perform DDL. The generic escaped predicate builder serves both DDL and SELECT; scope/order/key are indexed.
- JSON, CAS revisions and existing audit remain the sole durable Work authority. Index changes are transactional and schema-v1-compatible, do not rewrite JSON, and are maintained by every SQLite writer. Predicate changes replace only indexes for the same namespace/field; obsolete indexes are removed in that transaction. Indexes contain record identifiers/order only and no additional payload copy. Backup/restore and complete-release rollback own their lifecycle. Existing databases initialize at startup; short-lived reads remain correct before initialization. No new persistent registry or cache is needed.
- Recovery alone owns acceptance evidence, locking and lifecycle effects. CPU evidence extends the existing bounded known-good record (maximum eight retained releases) and inherits its permissions, audit and retention. It records only release/revision/process identities, timing and aggregate CPU, never commands, payloads or secrets. Historical attestations remain usable rollback evidence; they are not retroactively claimed to include CPU acceptance.
- Functional health and performance acceptance are independent. Watchdog never creates known-good and never interprets CPU failure as a restart trigger. Explicit attestation runs functional verification, 60 seconds warmup, thirty 10-second windows, functional verification again, then fenced persistence. Any sample failure, restart, authority change, invalid timing or expired evidence prevents acceptance. Evidence must be at most 60 seconds old when committed. Thresholds are mean <=5%, p95 <=10%, using CPU-time deltas/monotonic elapsed time, not lifetime ps percentages.
- The operator initiates acceptance with no user jobs and normal background scheduling. `/bin/ps` sampling supports the existing macOS/Linux Recovery deployments; unsupported/unreadable process counters cannot pass. Long or suspended sample windows are unknown. The six-minute read-only observation deliberately runs outside the exclusive Recovery mutation lock and fences every sample to the exact Runtime/release identity, so rollback/restart/activation remain available and any concurrent identity change invalidates the evidence. Final functional verification, identity re-check and known-good persistence run under the existing short Recovery operation lock. No process/daemon, admission rule, fairness rule, job priority or runtime-readiness state is added. Test dependency injection is in-process only, never exposed over MCP/CLI.
- Explicit rollback always reaches the existing stopped-owner, previous-manifest, execution-canary and bound-SQLite-backup checks. Healthy/known-good active status cannot convert an operator rollback request into success/no-op. Whole-runtime stop/switch/start/verify and compatible schema/backup rollback remain unchanged.
- Mutation identity/authentication, secret handling, release authority fencing, idempotent index initialization and outcome-unknown release reconciliation remain existing boundaries. Measurement failure leaves no new attestation; retries measure afresh. No external write occurs from a probe. No second readiness state machine or fallback owner is introduced.

## Accepted obligations

All accepted plan obligations are KEEP: indexed conservative query and domain ownership (Work/SQLite initialization); isolated call-cost diagnostics and remaining hotspots (validation); explicit fenced performance acceptance and rollback (Recovery); concurrency/backup/old-schema/Bun-Node tests, CPU threshold, candidate gates, external probes, clean scoped delivery and previous backup preservation (validation/delivery). No predecessor obligation is deferred or silently removed.

## Validation

Results are appended after focused tests, exact-candidate review, governed gates, and actual post-activation CPU acceptance. A passing query microbenchmark or functional probe is insufficient to declare CPU fixed.
