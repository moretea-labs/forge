# Work candidate CPU and explicit Recovery acceptance

## Evidence and decision (2026-09-12)

Runtime release `1789203347359-260ddf6c…`, authority revision 320, was observed at 108.8% CPU (one core = 100%). Forge had 749 Work rows, 748 terminal, approximately 13.5 MB of JSON. The JSON-exclusion query returned one row but scanned historical payloads and used temporary ordering. An in-memory copy measured median 23.983 ms before and 0.011 ms with a matching partial index (15 iterations). This establishes query cost, not whole-Runtime acceptance. A governed revalidation on a SQLite backup of the current Controller Home observed 750 Work rows (364 cancelled, 360 completed, 25 failed, 1 running): the production-shaped candidate query was median 8.791 ms / p95 12.022 ms and required a temporary B-tree before the derived partial index, versus median 0.005875 ms / p95 0.006583 ms after the index, with the planner selecting the candidate index directly and returning one candidate. The backup-only benchmark did not mutate live authority.

This consolidates the performance defect in `8193effd`'s unindexed prefilter and the existing Recovery auto-attestation/explicit-rollback defect. No new incident-specific service, status authority, scheduler or cache is introduced.

## Ownership and closure

- Work owns namespace, status semantics, terminal exclusions and conservative candidate normalization. SQLite owns the physical, derived partial index. Runtime composition calls Work initialization during its existing database startup stage, before hot readers/scheduler start. Queries never perform DDL. The generic escaped predicate builder serves both DDL and SELECT; scope/order/key are indexed.
- JSON, CAS revisions and existing audit remain the sole durable Work authority. Index changes are transactional and schema-v1-compatible, do not rewrite JSON, and are maintained by every SQLite writer. Predicate changes replace only indexes for the same namespace/field; obsolete indexes are removed in that transaction. Indexes contain record identifiers/order only and no additional payload copy. Backup/restore and complete-release rollback own their lifecycle. Existing databases initialize at startup; short-lived reads remain correct before initialization. No new persistent registry or cache is needed.
- Recovery alone owns acceptance evidence, locking and lifecycle effects. CPU evidence extends the existing bounded known-good record (maximum eight retained releases) and inherits its permissions, audit and retention. It records only release/revision/process identities, timing and aggregate CPU, never commands, payloads or secrets. Historical attestations remain usable rollback evidence; they are not retroactively claimed to include CPU acceptance.
- Functional health and CPU runaway acceptance are independent. Watchdog never creates known-good and never interprets CPU failure as a restart trigger. Explicit attestation runs functional verification, 10 seconds warmup, twenty 2.5-second windows, functional verification again, then fenced persistence. Any sample failure, restart, authority change, invalid timing or expired evidence prevents acceptance. Evidence must be at most 60 seconds old when committed. The `runaway-cpu-v3` safety ceiling remains mean <=25%, p95 <=50%, using CPU-time deltas/monotonic elapsed time, not lifetime ps percentages. With twenty windows, nearest-rank p95 is the second-highest sample rather than the single maximum, so one isolated burst is not sufficient evidence of sustained runaway. It is not the comparative release benchmark; candidate-vs-baseline <=10% attributable CPU regression remains governed by Release Evaluation/Benchmark authority.
- The operator initiates acceptance with no user jobs and normal background scheduling. `/bin/ps` sampling supports the existing macOS/Linux Recovery deployments; unsupported/unreadable process counters cannot pass. Long or suspended sample windows are unknown. The approximately one-minute read-only observation deliberately runs outside the exclusive Recovery mutation lock and fences every sample to the exact Runtime/release identity, so rollback/restart/activation remain available and any concurrent identity change invalidates the evidence. Final functional verification, identity re-check and known-good persistence run under the existing short Recovery operation lock. No process/daemon, admission rule, fairness rule, job priority or runtime-readiness state is added. Test dependency injection is in-process only, never exposed over MCP/CLI.
- Explicit rollback always reaches the existing stopped-owner, previous-manifest, execution-canary and bound-SQLite-backup checks. Healthy/known-good active status cannot convert an operator rollback request into success/no-op. Whole-runtime stop/switch/start/verify and compatible schema/backup rollback remain unchanged.
- Mutation identity/authentication, secret handling, release authority fencing, idempotent index initialization and outcome-unknown release reconciliation remain existing boundaries. Measurement failure leaves no new attestation; retries measure afresh. No external write occurs from a probe. No second readiness state machine or fallback owner is introduced.

## Accepted obligations

All accepted plan obligations are KEEP: indexed conservative query and domain ownership (Work/SQLite initialization); isolated call-cost diagnostics and remaining hotspots (validation); explicit fenced performance acceptance and rollback (Recovery); concurrency/backup/old-schema/Bun-Node tests, CPU threshold, candidate gates, external probes, clean scoped delivery and previous backup preservation (validation/delivery). No predecessor obligation is deferred or silently removed.

## 2026-09-20 policy correction

Recovery audit showed 18 rejected known-good CPU observations split into two disjoint populations. Six functionally healthy/cutover-complete observations formed a low cluster with maximum mean 10.34% and maximum p95 31.09%; twelve runaway observations formed a high cluster with minimum mean 90.64% and minimum p95 104.72% (up to mean 237.91% / p95 253.48%). There were no observations between the clusters. The original 5%/10% absolute threshold was not derived from a healthy whole-Runtime baseline; the initiating evidence was a 108.8% CPU runaway plus a query microbenchmark. It therefore conflated runaway protection with comparative performance benchmarking and repeatedly blocked healthy releases. Commit `b3b7912eb` had already reduced the observation to 10 seconds warmup plus ten 5-second windows; `eefefe163` later regressed only those constants back to six minutes without benchmark/statistical evidence while leaving the one-minute function comment intact. `runaway-cpu-v2` restored the bounded one-minute design and uses 25% mean / 50% p95 as a conservative safety ceiling: above the observed low cluster, but still less than roughly half the observed runaway-floor values. Comparative <=10% CPU regression remains a separate Release Evaluation/Benchmark decision. A 2026-09-22 live recurrence then exposed a second statistical defect: a functionally healthy candidate measured mean 9.44% but was rolled back because one of only ten 5-second windows reached 57.29%; with ten samples, nearest-rank p95 is the maximum. `runaway-cpu-v3` preserves the same 60-second budget and unchanged 25%/50% ceilings but uses twenty 2.5-second windows, making p95 the second-highest sample and requiring repeated high-tail evidence before the tail ceiling can reject a healthy-mean release.

## Validation

The isolated production-data copy contained 749 Work rows. Across the measured call sources, 20 active-candidate reads fell from 164.53 ms aggregate to 0.33 ms, while three lifecycle-projection reads fell from 25.59 ms to 0.10 ms. Index construction took 13.19 ms. A separate Node SQLite process passed indexed status transitions plus backup/restore. No Work payload was recorded in this evidence.

Focused SQLite/Recovery tests, type checking, Runtime architecture, architecture sync, bootstrap checks, affected tests, and the governed main gate passed on the candidate. Independent review identified and closed two timing gaps: functional verification is fenced to the same process/release sampled afterward, and every 2.5-second warmup/sample window rejects suspension beyond 3.75 seconds. Post-activation CPU evidence is now an approximately one-minute `runaway-cpu-v3` safety observation; comparative performance regression remains a separate governed Benchmark/Release Evaluation concern.
