# Forge App Store Connect Integration

Forge exposes App Store Connect as an optional first-party provider behind the stable plugin policy, Process Runtime, receipt, and audit boundaries. Credentials remain external to repository state. Remote mutations require explicit authorization and idempotent provider evidence.

See [Plugin management](forge-plugin-management.md) and [Verification and Release Gates](architecture/CURRENT.md).

## Screenshot processing

`upload_app_screenshot` verifies the exact App, editable iOS version, localization and display set, then confirms the committed screenshot checksum through the official API. It observes the same screenshot ID for up to 45 seconds. `processingComplete: true` requires `COMPLETE`; `processingComplete: false` means the committed asset remains in `UPLOAD_COMPLETE`. Use `list_app_screenshots` to observe that asset before claiming storefront acceptance.

A failed state, mismatched checksum, ambiguous filename or unresolved commit is an explicit error. Do not reserve a replacement or resend bytes to resolve it. Repeating an upload whose checksum is already committed resumes processing observation. Screenshot reordering accepts only the exact existing set of completed assets.

## Release, IAP and ASO API coverage (source v1.10.0)

- **Release preflight:** `check_release_readiness` reads the exact App Store version's parent App, assigned Build, version localizations and App Review contact details. A passing local preflight is only `candidate_unverified`, **never** a claim that Apple will accept the review submission. Remaining privacy, territory, age rating, screenshot processing, export compliance and Apple-side requirements are checked by the official submission result. Separate create/attach/submit actions retain their strong-confirmation policies.
- **IAP and subscriptions:** Typed v2 IAP product/metadata-version/localization actions, subscription-group and subscription metadata versions, price-point and territory schedule reads, and separately gated price schedule creation. The old direct-parent localization endpoints are deprecated in Apple's API 4.4.1 model; new authoring relates localizations to a **version**. Price changes can affect customers irreversibly: use `dry_run` and verify the chosen Apple price-point/territory IDs before any authorized write.
- **First-party ASO history:** Analytics `ONE_TIME_SNAPSHOT` and `ONGOING` requests, report/instance/segment reads and checksum-verified compressed TSV segments. List actions expose Apple's opaque cursor; each read returns Apple's authoritative paging links. Segment preview returns up to 500 rows (default 100), with a 16 MiB compressed / 64 MiB decompressed limit; use multiple segments rather than silently truncating history. Sales/Finance reports require an eligible **team** API key and vendor number; individual keys may lack these permissions. No new local Analytics store or automatic reporting job exists.
- **ASO interpretation boundary:** App Store Discovery/Engagement source dimensions, impressions, product-page activity, downloads and territories can be analyzed from available Apple reports. Neither this connector nor Apple Analytics provides arbitrary third-party keyword rank, competitor ranking, or historical search volume. App Store keyword configuration is distinct from search-rank observations; Apple Ads is a separate API and authentication boundary.
- **Safety and availability:** Configuration and credentials remain Controller-global. The checked-in adapter is source code; it is **not** live in the installed Runtime until a separate, authorized Runtime release/activation. No App upload, TestFlight distribution, review submission or real pricing mutation occurs through reading, testing or staging source changes.

- **2026 App Asset Library:** Call `get_app_asset_library` (`GET /v1/apps/{id}/assetLibrary`) first to obtain the `appAssetLibraries` ID, then `list_app_asset_library_images` or `list_app_asset_library_videos` against `/v1/appAssetLibraries/{libraryId}/images|videos`. `list_app_asset_library_reference_data` reads Apple's current size/format specifications. Do **not** infer the library ID from the App ID or use non-existent `apps/{id}/appAssetLibraryImages` paths. Legacy screenshot set operations remain separate from the reusable Asset Library workflow.

- **TestFlight and Xcode Cloud:** Beta group/tester management reads and writes are available through exact `betaGroups`, `betaTesters` and relationship endpoints; new invitations, public link changes and tester assignments require strong confirmation. `get_xcode_cloud_build_run` and `list_xcode_cloud_build_actions` inspect Apple run status/actions; `start_xcode_cloud_build` can incur Xcode Cloud usage and always requires strong confirmation. These APIs do not replace Forge's local Xcode build/device execution. No TestFlight invitations or Xcode Cloud builds are automatically triggered.

- **ASO grouped history:** `summarize_analytics_segment` retrieves one Apple segment with MD5 verification, then groups a numeric report column such as `Counts` by one or two exact Apple TSV columns such as `Date`, `Territory` or `Source Type`. It supports an exact-value dimension filter and returns capped top groups, total/distinct-group counts, excluded rows and truncation flags. It never claims that a single segment is an entire report or that a filtered source represents organic keyword ranking. Apple's `App Store search` source also includes Apple Search Ads results; do not infer pure organic acquisitions from it. For longer history, list every relevant report instance and segment and reconcile all partial results; no automatic ingestion, cache or local analytics authority is created. Do not sum unique-user counts across dates as though they were distinct users over the whole period.

- **Additional official reads (v1.5.0):** The plugin now inspects App Store Connect team members, roles, outstanding invitations, and the apps each user can access; App Store Connect webhook configuration and delivery status; age-rating declarations, App Store categories and published accessibility declarations; modern App Store product page experiment resources; and Apple's power/performance metric reports for an App or Build. Power/performance reads request Apple's vendor JSON MIME type. This release adds no access-modification, invitation, webhook-create, or webhook-delivery retry writes; those are separate, higher-impact future operations.

- **Complete instance aggregation (v1.6.0):** `summarize_analytics_instance` retrieves the Apple-owned segment list for one report instance, verifies every signed gzip segment's checksum and groups the requested numeric column across all of them. It requires that the entire instance fit into the bounded limit (default 8, maximum 12 segments; 64 MiB cumulative compressed) with **no** unconsumed API pagination and no truncated intermediate groups; otherwise it rejects instead of showing misleading totals. Results are complete **for that instance only**, not for every historical period. Apple may also suppress data under privacy thresholds. No recurring fetch/daemon/storage is created.

- **TestFlight access removal (v1.7.0):** `remove_beta_tester_from_group`, `remove_build_from_beta_group`, `send_beta_tester_invitation`, `delete_beta_group` and `delete_beta_tester` use Apple's exact beta group/tester relationship and invitation endpoints. Every removal and invitation is an authorized strong-confirmation write and exposes `dry_run` to inspect target IDs and payload. Group deletion revokes access to its builds; deleting a tester revokes testing access across **all** Apps, so the latter requires especially careful confirmation. Apple may respond with HTTP `202 Accepted` for asynchronous revocation, which only acknowledges receipt; don't claim all access is gone until a subsequent official read confirms it. The Analytics instance aggregator refuses missing MD5 checksums, empty/not-yet-ready segment lists, incomplete pages and excessive dimensions rather than incorrectly reporting `complete: true`.

- **Analytics request lifecycle (v1.8.0):** `get_analytics_report` and `get_analytics_report_instance` read official report metadata and processing dates. `delete_analytics_report_request` previews `DELETE /v1/analyticsReportRequests/{id}` and requires strong confirmation before a real call; deleting a request stops its associated ongoing report generation and should never be treated as a housekeeping read. Apple documents **Admin** access for requesting/deleting reports, whereas other eligible roles can only read/download. A new `ONGOING` request may require 1–2 days for initial generation; `ONE_TIME_SNAPSHOT` does not continuously update. Use `get_analytics_report_request` to read current `stoppedDueToInactivity` rather than inferring report readiness from the request's presence. No polling schedule or background task is created.

- **App Review secret boundary (v1.8.1):** Apple responses can include `appStoreReviewDetails` with `demoAccountPassword` in the primary resource or an included JSON:API relationship (for example a version fetched with `include=appStoreReviewDetail`). The canonical ASC API response handler redacts that field before returning data or provider errors to tool consumers; review contact metadata and non-secret status fields remain available. Never present or persist Apple's reviewer demo password in a Forge plugin result, log or issue.

- **Release/read coverage (v1.9.0):** `get_app_store_version_phased_release` exposes Apple's current phased rollout state/day; `get_app_store_review_detail_by_id`, `list_app_store_review_attachments`, `get_app_store_review_attachment`, `list_app_store_review_attachment_ids`, `get_review_submission_item` and `list_review_submission_item_ids` inspect official review resources. Attachment processing state or review submission item state is **observation**, not acceptance. All response shapes, including nested App Review detail resources, pass the canonical demo-password redactor. These new actions are read-only; upload, phased-release mutation and review submission remain separately authorized.

- **Staged rollout mutations (v1.10.0):** The official `appStoreVersionPhasedReleases` create/update/delete endpoints are now exposed through typed strong-confirmation, dry-run-capable actions: `create_app_store_version_phased_release`, `update_app_store_version_phased_release` (`ACTIVE`, `PAUSED`, or `COMPLETE`), and `delete_app_store_version_phased_release`. Creation starts from the Apple `INACTIVE` state; deletion is only supported by Apple for an unstarted phased release. `COMPLETE` can immediately deliver an update to all eligible automatic-update customers and is not reversible; it must never run implicitly as part of review preflight, App Store metadata editing, or auto-release. Apple remains authoritative about whether a version is eligible (phased release is unavailable for an app's first version), and the current state should be read before any separately authorized mutation. No actual Apple phased-release mutation was executed during this source change.
