# Forge Current Architecture

## Decision

The operator has withdrawn authorization for unattended ChatGPT CONTINUE to CONTINUE to DONE automation. Real release-bound evidence repeatedly showed applied effects without trusted completion receipts, followed by timeout-based migration and another applied effect. The system must not infer model acceptance from DOM, idle state, HTTP success, CI, or scheduler health.

Retire autonomous model-turn continuation instead of adding another completion observer, retry loop, provider, scheduler, or duplicate authority. This is a source migration decision, not authorization to activate/restart/cut over the current Runtime.

## Kept capabilities

1. **Launch Session** is an explicit bounded action. It opens or attaches one selected session (ChatGPT or supported external CLI); an explicitly requested prompt may be dispatched at most once using the existing delivery/authorization owner. Return exact session identity and an honest dispatched/not-applied/unknown delivery receipt, never a model task completion. A transport-unknown external mutation is not retried automatically.
2. **Schedule** retains canonical schedules, trigger admission, one occurrence identity, one bounded explicit action, and occurrence receipts. Work-free browser watch is observe-only; resolving a Handoff persists a decision without rearming ControllerRound or waking a model. Existing create/get/list/pause/resume/delete/manual trigger remain. Schedule reports whether its explicit dispatch occurred; it does not invent next-round CONTINUE, infer DONE or migrate the conversation.
3. The model or user owns planning, results interpretation, additional manual launches and task acceptance. GitHub Issue and Project remain progress authority. Forge Process/Git/permission/release safety authorities remain unchanged.

## Safety and final acceptance

- Stop active autonomous Task through its sole owner before source retirement; do not cancel/replay an applied external Send or delete the user's conversation.
- Migrate all direct and indirect callers; update architecture/build manifest and targeted tests; delete dead code rather than retaining disabled parallel paths.
- Confirm Work-free manual session launch; Schedule create, trigger, receipt, pause/resume and restart safety; no auto CONTINUE/migration/second Writer; unknown dispatch not repeated.
- Require current executor exact-HEAD diff verification, focused type/architecture checks and CI; independent review only on explicit request. Current Runtime remains untouched until approval of a particular release activation.
- Source merge records code integration only; GitHub Issue #313 remains OPEN until Work-free Launch Session and Schedule occurrence/receipt/restart/no-replay are verified on a specifically authorized Runtime release.

### Xcode DerivedData resource claims (Refs #478)

Process Runtime resolves an explicit literal `xcodebuild -derivedDataPath` against the actual execution cwd, canonicalizes existing symlink ancestors, and claims the physical cache path through the existing Lease owner. Distinct caches retain independent cache identities across checkouts; equal or ancestor/child paths conflict across repositories. Host capacity additionally serializes native Xcode build/test actions through the existing `host-service:ios-build` Lease across repositories and plugin/terminal/check entrypoints; typed read-only Xcode inventory is exempt. This admission bound supersedes unrestricted disjoint-cache build concurrency, without widening checkout/cache ownership. Each concrete cache also holds a repository build-cache read claim, so an opaque/default-cache build's existing write claim remains exclusive. Dynamic or opaque compound shell commands, dangling symlinks, duplicate cache arguments and output/cache overrides retain that conservative repository claim. Native XCTest commands additionally retain the host-wide simulator-test write claim. This changes command resource admission only; it does not create a scheduler, build executor or progress authority.

An exact argv-only `git push --force-with-lease=refs/heads/<review>:<sha> origin :refs/heads/<review>` is a remote-only deletion, not a local Checkout/HEAD/index mutation. Process Runtime may reuse its existing repository `remote:<repoId>` exclusive Lease instead of a workspace/Git-ref writer, allowing an unrelated dirty Work to retain its source ownership. Only a single, syntactically safe, non-protected branch whose deletion refspec exactly matches the expected SHA lease qualifies. Shell commands, unknown arguments, unleased or protected refs retain the previous conservative claims; Git command classification remains destructive/authorization-gated, and the remote's SHA CAS decides actual deletion. This optimization neither proves a GitHub PR was merged nor creates a remote branch cleanup authority; that decision stays with existing Git/GitHub evidence and the caller.

### Warm iOS Simulator admission (Refs #192)

Forge's existing iOS plugin Simulator action and XCTest helper read the native available-device inventory before requesting an iOS Simulator boot. An exact already-Booted UDID is reused (with bootstatus readiness verification), without redundant boot or cleanup; smoke review already defaults to keeping the device warm after releasing its action/Process resource. New device boot requests fail closed when **two iOS Simulators are already Booted**, with current device identities and an explicit capacity error rather than evicting an unknown owner. watchOS devices do not consume this iOS cap; unknown inventory or transient device state does not grant admission. Plugin and Process admission continue to use the existing host-service:ios-simulator-test resource Lease; there is no second pool registry, daemon or boot-state writer. Xcode UI-test helper resolves its destination to an exact admitted UDID before invoking Xcode, preventing implicit boot of another named Simulator. A caller explicitly requiring another device must first choose an already-booted compatible target or retire one genuinely idle device through its owning workflow, never age-only forced shutdown.

This cap covers Forge-managed Simulator boot/test actions, not arbitrary external shell processes executing xcrun or xcodebuild outside Forge. Those callers must migrate through the canonical Process/plugin admission or use the same bounded device constraints in their existing test runner. Child process cleanup and host-wide native compiler/test capacity belong to the existing #261 Process/child-supervisor owner, not a Simulator boot scheduler. Actual installed-Runtime cross-entry lease/no-orphan acceptance remains open under #192.

### Requirement, Plan, and historical Work

Requirement is the semantic outcome authority. Its SQLite revision owns the outcome, acceptance criteria, explicit open/completed state, `progressSummary`, `remainingWork`, and `acceptedEvidenceRefs`; `requirement_revise` uses expected-revision CAS and `requirement_get.progress` reads the Requirement directly. Plan is optional model-authored planning context with its own revision and provenance. Neither Requirement nor Plan owns a checkout, process, provider turn, Git mutation, or external effect.

Work lifecycle is retired. Existing Work and WorkHandle records remain readable only for audit, migration, provenance, and bounded historical queries. The public Work surface is historical `get/get_contract`; current execution must not create, revise, complete, relocate, prepare, bind, or recover Work as a mutable lifecycle object. A historical `work_id` cannot grant mutation authority, select a checkout, attribute a Process, own a Schedule, determine current automation status, or veto ordinary Git delivery. Historical records may be consulted by explicit legacy cleanup to avoid deleting unproven source, but they never become current liveness or ownership authority.

### Repository source, edit, validation, and cleanup authority

Git and the registered checkout/worktree identity own repository source and placement. EditSession owns one bounded patch transaction and its after-image; its durable identity is repository/checkout/principal, not Work. Process Runtime owns command execution identity and exactly-once attachment; Resource Lease owns physical conflict admission; Check receipts own validation evidence for exact inputs. Git SHA/CAS, index/ref locks, path scope and dirty-source checks remain the repository mutation fences.

Ordinary worktree creation and source edits do not require semantic Work. Structured worktree retirement proves the exact registered checkout, source HEAD, physical identity, cleanliness, live Process/Lease state and Git containment before removal. Historical WorkHandle or OwnedResource evidence may cause an explicit legacy-cleanup path to preserve uncertain bytes, but it cannot authorize mutation or re-create Work ownership.

### Technical design baseline

- **Source acceptance is outside Runtime.** PR/CI and the accepted merged source revision own source-correctness evidence. The retired ExecutionJob `release-gate` may not re-read Issue/Task, Agent/Local Job, EditSession, integration, or verification state to veto a Runtime release. Runtime and Standalone Recovery consume an exact immutable artifact and keep only physical safety/readiness responsibilities; the public `request_release_gate` remains an external-controller evidence handoff, not a second acceptance authority. The normal release path is now two mechanical operations: `stage_runtime_release` materializes one model-selected exact accepted 40-hex source revision into the canonical Stable Controller Home immutable release store without changing Runtime authority, SQLite or services; `activate_runtime_release` then requires that release's `sourceCommit` plus the caller-observed active release id and RuntimeReleaseAuthority revision to match exactly before the existing fenced stop/publish/start/verify/compensation transaction may run. Portable describes artifact mobility, not a requirement for a second Controller Home. ReleaseSession/Candidate B remains only for explicit incompatible migrations and historical persisted-session reconciliation; historical `static_verified` remains readable compatibility evidence only and is not part of normal release.

- **Repository delivery is Git-owned.** Ordinary repository mutation enters the registered checkout/EditSession/Git path directly. Commit and integration use exact branch/HEAD/index/path scope plus Git/ref/resource fencing; no WorkHandle or semantic Work is required to authorize or settle the mutation. Source merged, active Runtime, and user-visible end-to-end acceptance remain distinct facts.

- **Source freshness is explicit Git provenance.** Default-branch refresh updates only the selected tracking ref under the existing Git/resource fences; an explicit base ref remains caller-selected provenance. Existing checkouts are never silently rebased, and source freshness does not create a semantic execution owner.

Repository commands use the selected registered checkout and Process Runtime with ordinary preview, authorization, timeout, immutable execution identity and resource claims. New command execution rejects Work attribution; historical Work identifiers are available only through explicit read-only history surfaces.

The legacy MCP PRD/Sprint/Plan Markdown generators, dedicated PRD/Sprint listing tools, `summarize_forge_state` and `append_controller_plan_note` are retired. Model-authored semantic Requirement and Plan remain in Controller Home; historical Work is read-only compatibility. Intentional human-authored project documents use ordinary repository inspection and Direct Edit.

The MCP Gateway does not maintain a second ExecutionJob creation authority: its uncalled `shouldCreateDurableJob` predicate and duplicate retired-creation flag have been removed. The canonical Gateway classification directly refuses retired durable submissions; `execute_command` remains under its existing Repository/Process authority. Historic ExecutionJob read, scheduler reconciliation, bounded legacy worker recovery, grants, and unknown-outcome fencing are unchanged. An empty current active index is observation, not permission to discard historical recovery. This is a source-boundary simplification, not evidence of faster end-to-end delivery.

This authority applies one default design rule across new architecture and refactors: **Forge is thin but capable — stateless in coordination, stateful in facts, optimistic in concurrency, and explicit in effects.** The model/controller owns reasoning, workflow policy, validation strategy and semantic completion; Forge owns durable facts, execution capabilities, mechanical correctness and recoverable effects. Cognitive learning follows the same split: the model authors reusable semantic deltas and usage judgments, while the shared MCP transport may settle that bounded advisory metadata after any successful meaningful ordinary tool outcome; routine micro-steps do not create a learning lifecycle.

- **Ordinary Context search does not implicitly start the TypeScript compiler.** A plain `rh_context.search` in `implementation` mode with `structural_context=off` materializes bounded raw line windows (or a complete small file) without spawning the TypeScript symbol Sidecar for every long `.ts`/`.tsx` candidate. Explicit `plan/debug/review` or structural retrieval retains existing declaration-range enrichment; explicit `semantic_navigation` continues through its existing typed provider. Source/file policy, raw SHA provenance, snippet truncation markers, and fallback windows remain authoritative. No cache, new provider, or second search route is introduced.
- **One physical repository lock for active Edit Session entrypoints.** Legacy MCP begin/apply/savepoint/rollback/finalize and Local Bridge direct rollback/finalize share the existing repository-scoped Controller lock used by safe patch. Local Bridge rollback/finalize hold that lock across an isolated worker's synchronous editor operation and use the same existing Process-lease admission check, so those two HTTP requests no longer block the Local Bridge event loop; worker failure without a result is an unknown mutation outcome requiring durable session inspection, never blind retry. The MCP multi-repository facade does not nest a second repository lock around the five legacy editing mutations: their inner existing owner performs the physical lock and Process-lease check once. The edit-session kernel remains the sole backup/hash/CAS/session-journal writer. Remaining legacy MCP editing and legacy completion/integration still execute synchronously; completion retains its established integration-before-repository lock ordering and is not yet an off-thread delivery path. Local Bridge savepoint creation also uses the existing repository lock, and verification persists evidence under that single physical writer while executing its checks in the existing Local Bridge edit worker. The historical finish route already locks within the completion orchestrator and must not be double-locked in HTTP.
- **OAuth credential writes do not place secrets in subprocess argv.** Existing Google and Resend OAuth/SMTP Keychain writers share one macOS `security -i` stdin-only write primitive; `/usr/bin/security` receives no secret argv/env and its potentially echoed interactive stdout/stderr is discarded rather than logged. Since `security -i` can report process exit 0 for a failed command, the same isolated OS Keychain is immediately read back and compared in-process, failing closed without returning/logging the value; successful write status alone is not trusted. CR/LF/control-character payloads are rejected instead of being interpreted as additional security commands. This is a transport hardening of the same OS Keychain, not another Vault/provider/authorization authority; real L1 enrollment and native credential-field fill still require their own end-to-end proof.
- **Terminal ChatGPT conversation capacity is not dependent on old transcript hydration.** The existing Supervisor Browser observer accepts an exact bound-conversation URL plus a live provider-owned terminal capacity banner even if historical turns are not loaded, and delegates the fresh handoff to the same Supervisor CAS migration. Quoted transcript/activity text, unverified URL, applied source without a receipt and unknown dispatch remain non-migration evidence; no second sender or conversation owner is introduced.
- **Canonical Grant mutation cannot silently revive an extant revoked ID.** The existing Kernel Grant writer leaves expired/revoked rows intact during routine dedupe, refuses reuse of their IDs while retained, forbids principal/owner/target/capability/scope/risk/constraint changes under an active ID, does not deduplicate distinct active scope/risk/constraint grants, and its existing active-grant query requires exact restricted-context matches instead of silently authorizing a constrained Grant through an unconstrained request (the generic Capability Broker does not yet provide provider-attested context and must reject these restricted grants, while the existing Plugin authorization consumer passes its own exact canonical plugin metadata constraints), and preserves the original issuance/expiration times on an active same-ID replay (only its update timestamp can advance). Explicit `reconcileCanonicalGrants` still prunes revoked/expired rows by its existing lifecycle policy (#243); this slice is not permanent audit retention or post-prune ID-replay protection. Fresh authorized enrollment uses a distinct identity, but identity enrollment and real L1/L2/L3 native verification remain pending under #288. Existing one-shot console unlock is unchanged; no second Vault or permission authority is introduced.
- **Gateway latency evidence stays a read-only, process-local projection.** Existing bounded lock-wait and mutation-gate P50/P95 samples are filtered by the selected repository and exposed only through `rh_status(detail)`, with `not_observed` for empty buckets. They are not persisted or joined across processes, do not measure end-to-end Edit Session or Context latency, and never establish live speedup without matched active-release measurements. Summary status remains unchanged; no metrics authority, Provider, or instrumentation side-effect is added.
- **One Git status header owns branch/upstream observation.** The existing `git status --porcelain=v1 --branch` output already contains the current branch and upstream. The structured Git status reader reuses that information and only starts one `git rev-parse` for the exact HEAD SHA, replacing four synchronous Git process launches with two on the ordinary path; unfamiliar status headers use the existing Git read fallback rather than fabricating an identity. This reduces `work_inspect` summary Git calls from four to two and detailed/Work validation from ten to eight without changing Git permissions, dirty-path evidence, or Work fencing.
- **Work inspection observes Git once per request.** `work_inspect` defaults to a status/changed-path summary without staged or unstaged patch generation; `detail` computes bounded diffs only on request. Detailed workspace inspection and Work validation reuse the same branch/HEAD snapshot rather than relaunching Git for each diff slice; an omitted patch is explicitly marked, not presented as an empty diff. Existing Git ownership fences and live status authority remain unchanged.
- **MCP tool admission reuses the static published surface.** `tools/call` name admission and the Canonical Runtime schema fingerprint fence read the same existing cached static tool definitions as tool discovery, without loading access-mode configuration or assembling a diagnostic tool inventory on every call. Request versus Full Access remains enforced by the existing action authorization path; detailed diagnostic exposure reports still resolve actual access state. No new tool registry, cache or gateway authority is introduced.

Unregistered retired Agent names continue through the ordinary `TOOL_NOT_FOUND` result rather than retaining an unreachable compatibility branch. No new cache, dispatch table, permission owner, or execution lane is introduced.

It is a compatibility bridge pending retirement of ControllerLock editing paths into one lease owner; legacy MCP and Completion work remain synchronous; Local Bridge finalize/rollback run off-thread under the same lock and lease handshake, without claiming a Process lifetime handoff or live P50/P95 acceptance.

No extra Provider or Controller is introduced. This closes a Process-to-Process claim bypass, but legacy editor entrypoints still need migration to this same resource authority before cross-surface physical mutual exclusion can be claimed. Existing runtime identities and unknown-result receipts remain authoritative.
- **Legacy completion shares the existing physical repository writer.** Before Requirement portfolio cutover, Issue/Task completion keeps its existing integration-target lock and additionally holds the same repository mutation lock as MCP/Local Bridge Safe Patch for the complete integration/edit/rollback/commit transaction. Lock ordering is fixed (integration then repository); nested edit primitives never reacquire it. A missing canonical repository identity fails closed, and migrated legacy completion still rejects before taking a lock. No new lock owner or competing writer is introduced. This is prerequisite fencing, not yet off-event-loop edit execution or live speed proof.

It never substitutes the enclosing repository for an ordinary directory or follows file symlinks. All nesting shares the existing path/byte budgets and one five-second Git-read deadline; bounded Git reads disable optional locks and fsmonitor, do not inherit alternate Git/index environment, and never update the nested index or refs. Git-ignored files and the existing `.ai/harness` exclusion retain the same source-input semantics as the parent snapshot. This adds no registry, writer or receipt authority; a nested input change invalidates reusable verification evidence.

The generic browser RPC likewise cannot attest a negative dispatch outcome; only the in-process Computer dispatch owner may write that proof. Unknown provider mutation never becomes retry authority through an observer.
- **Events trigger; state decides.** Duplicate wakes/recovery demand coalesce around canonical occurrence/effect identity. Contention is a scheduling condition rather than semantic failure when the operation can run later.
- **Context review reads the exact Work checkout.** `rh_context.search(work_id=...)` resolves current source evidence through existing WorkContract placement and WorkHandle, then Repository Registry. It never silently reads dirty canonical main when a managed Work has a different checkout. An explicit conflicting checkout, unavailable/retired Work target, or WorkHandle HEAD drift fails closed; no second source-routing authority, provider, cache or Work lifecycle. Semantic-only Work without physical placement retains the caller's explicitly selected repository scope; capability and cognitive-only reads are unchanged.
- **Independent Review/CI changes notify the original Supervisor, never authorize its merge.** A reviewer that has read the current GitHub PR and fixed HEAD through the GitHub provider can call the existing `supervisor_task review_notice` action with exact task/repository, PR, reviewed/current SHA and review/CI receipt. Standalone Supervisor does not accept arbitrary WAIT; the original task's next legitimate CONTINUE atomically consumes notices in the same completion-to-effect transaction, without another Writer, Scheduler, external Send or unknown-effect replay. The outgoing prompt prominently labels every outcome unverified and rechecks independent review/CI, current HEAD, permissions and single merge Writer before any integration. A stale REVISE remains advisory; an old-HEAD ACCEPT is never merge approval. On explicit original-task `supervisor_task review_watch_bind` for an exact GitHub repository and PR, the same Runtime Supervisor maintenance tick additionally performs a bounded read-only GitHub CLI observation every 30 seconds (up to four opt-in PR targets per tick, round-robin), verifies `origin` matches the requested GitHub repository, and journals platform `APPROVED` / `CHANGES_REQUESTED` / `DISMISSED` plus terminal check-run outcomes as **unverified notifications**. `COMMENTED` prose is never formal approval. Duplicate observations are idempotent, closed PRs retire their existing event-bound watch, and non-GitHub tasks make no GitHub calls. No webhook, separate Scheduler, review state machine, second Writer, direct provider Send, or merge authority is introduced. Full autonomous model REVISE→same-PR fix→independent new-HEAD review→merge→live E2E and Runtime known-good proof remain separately required.

## Product model

The model owns interpretation, planning, trade-offs, validation strategy and the decision that a Requirement is complete. Requirement is the durable semantic outcome/progress record; Plan is optional planning context. GitHub Issue/Project is the human-visible project-progress surface. Forge does not manufacture a second task lifecycle for ordinary coding.

`launcher_start` is a one-shot, Work-free session open/bind operation. It may create or attach the selected Computer/ChatGPT session but never auto-sends `CONTINUE`, enrolls a Supervisor, or claims that a model turn completed. Provider/session identity is transport state, not project progress.

Schedule owns independent trigger policy, one occurrence identity, admission and one explicitly authorized bounded action. Legacy `external_controller_wake`, `controller_progression`, `chatgpt_browser_prompt`, personal-assistant routines, and any Schedule carrying `work_id` are retired and fail closed before a new occurrence can replay a model turn. Historical records remain visible as read-only audit; they cannot be resumed or manually run.

External effects keep stable request/effect identity and explicit applied/not-applied/outcome-unknown semantics. Reads may retry where provider semantics allow it; ambiguous non-idempotent writes must be observed/reconciled before any replay. Browser/Computer target identity, authentication and exact-target fencing remain provider-owned facts and never become a semantic task authority.

## Runtime performance acceptance

Runtime CPU diagnostics retain the `runaway-cpu-v4` sustained-consumption rule: after the existing warmup/window observation, a diagnostic sample is rejected when mean CPU exceeds 25% or at least half of windows reach the 50% ceiling. This evidence is diagnostic/performance evidence; it never becomes rollback or semantic-completion authority.

Recovery known-good is a **recoverability attestation**, not product/performance acceptance. It requires strict whole-Runtime verification of the exact active immutable release, coherent RuntimeReleaseAuthority, the manifest-attested execution surface, and a durable validated recovery bundle containing the release, SQLite backup, and service contract. Product E2E, source correctness and performance evaluation remain independent evidence owned by their respective workflows.

ReleaseSession Candidate B storage is durable authority only for explicit incompatible-migration progression and its rollback transaction; it is not an authority on the normal compatible release path. RuntimeReleaseAuthority remains the physical active/previous immutable-release pointer. Release and Recovery may stop/start only through their fenced transition owner; status/readiness projections do not become lifecycle writers.

## Controller efficiency contract

- The optimization unit is a **semantic checkpoint**, not a single low-level operation. GPT may issue one intent that mechanically fans into several bounded reads/searches or one coherent edit-plus-validation transaction when the implied steps require no new semantic judgement.
- Forge may execute deterministic conditionals such as `check failed -> collect bounded diagnostics and failure-site source`; it must stop before semantic actions such as choosing a repair, widening product scope, or deciding that acceptance is satisfied.
- Controller turns should stay continuous through a coherent implementation slice. External Controller relay is for real continuity boundaries such as scheduling, long waits, context/session rollover, or unattended resumption, not a normal inner-loop coding primitive.
- Operational output is aggressively bounded, while source/diagnostic evidence may use a larger information budget when that reduces repeated controller round trips. Every evidence bundle remains source/revision identified and reports truncation or coverage gaps rather than claiming semantic completeness.
- ChatGPT-native perception/compute capabilities are not copied into Forge merely to centralize tools. Web/Vision/one-shot connector perception may stay controller-native; Forge owns the local or durable execution/evidence boundary. A separate ChatGPT sandbox is never repository source or build authority.

## Context engine

- Reuse the current conversation working set: read necessary Work/Plan/decisions and relevant source once, then fetch only missing or changed evidence. New conversations restore minimal current durable task facts, not full chat history. Known source paths normally use exact reads; `rh_context` discovery is for new dependencies or insufficient context. Relevant HEAD, dirty paths, Writer/leases, permissions and external-effect outcomes remain live operation-boundary checks.
- `rh_context.search` defaults to a compact `summary`: current source snippets and SHA identities, the intact Context Closure receipt, readiness, denials and coverage-gap counts remain inline. `detail`/`raw` adds retrieval diagnostics, omitted candidate paths and explanatory metadata through the same read path; there is no second context store or automatic retrieval cadence.
- For exact or selected source paths, `rh_context` resolves applicable repository guidance by walking only that path's bounded directory ancestry from repository root to the nearest directory and returning present `AGENTS.md` / `CLAUDE.md` files in `instructionContext`. These files are guidance-only evidence: they do not consume the source `max_files` budget, define semantic scope, or become lifecycle/architecture authority. Missing optional guidance files are normal; policy denial, read failure, or bounded truncation stays visible as a coverage gap.
- The first request may perform one broad parallel discovery fan-in; natural-language lexical terms are heuristic hints, not completeness obligations. Discovery ranks the full authorized ripgrep match set by distinct-term coverage and inverse document frequency before applying the bounded candidate budget, so early alphabetic matches cannot hide a later file that better covers the query. The remaining coverage gap stays explicit; exact known-file and compiler-semantic retrieval remain strict.
- Once credible paths or symbols are discovered, the semantic controller derives the next retrieval from returned source and prefers exact known paths, compiler-backed symbol navigation, or structural relationships over repeating the same broad lexical scan. Follow-up requests reuse in-process/session caches.
- Exact known paths reserve retrieval budget and current raw source is authoritative.
- Complete small files and complete matched symbols are preferred over arbitrary line windows. Bounded source materialization never character-cuts a declared source range while reporting the original line bounds: oversized symbols are split into contiguous whole-line snippets, and if the file snippet budget is exhausted the final returned chunk is explicitly marked `truncated` with its actual end line. Partial source therefore degrades readiness instead of masquerading as complete code.
- Ordinary source discovery uses bounded lexical/raw evidence by default without starting CodeGraph or requiring its index freshness. The integrated CodeGraph index and its Runtime bundle are retired; explicit symbol requests use existing language-service navigation. Stale structural evidence must be labeled and current changed files remain raw-source authoritative.
- TypeScript Language Service navigation provides compiler-backed definition/reference/implementation lookup for TypeScript symbols through `rh_context`. Requested locations are also returned in a bounded flat `semanticEvidence.locations` projection so generic facade depth bounding cannot replace actionable path/line/column evidence with placeholders. Swift uses the same bounded `semantic_navigation` route with SourceKit-LSP, but only on explicit symbol requests and only when SwiftPM, BSP (`buildServer.json`), or compilation-database build settings are already available; Forge never performs an implicit build/index just to answer context. Xcode projects use `xcode-build-server` as the build-settings bridge. Because a present BSP can still return generic inferred flags instead of target settings, explicit Swift navigation verifies xcode-build-server compiler-option quality before starting SourceKit; obviously fallback options are rejected as incomplete. Manual `.compile` data produced from real `xcodebuild` output is validated locally, while automatic xcode-build-server mode uses a short cached BSP probe. SourceKit sessions are started lazily, serialized per repo/workspace, kept for a short two-minute idle TTL, and resynchronize changed open files; the first explicit Xcode semantic request has a bounded cold-start budget while warm requests retain the tighter interactive budget. Ordinary `rh_context` calls do not start either the BSP probe or SourceKit. Missing/stale/fallback build settings degrade explicitly to current lexical/raw source evidence rather than returning a false complete closure.
- MCP tool names and input schemas are a deployed client ABI because approved ChatGPT apps may retain a frozen action/input snapshot. The current registry exposes every registered capability; historical conversations may still hold an older bounded snapshot until reconnect. Core quality capabilities therefore need a path through already-stable facade fields. `rh_context` supports precise `@tsnav` and `@swiftnav` directives in `query` as compatibility paths; refreshed clients may use the existing structured `semantic_navigation` field. For a newer semantic facade operation or newly required semantic field that an old `rh_work` schema cannot express, `operation=repair` plus `capability_id=semantic.v1:<bounded-payload>` is the generic transport-only compatibility envelope. The server owns an explicit per-operation allowlist and exact payload schema. The current allowlist admits `requirement_create` and `plan_create`: Requirement creation keeps `requirement_id` explicit outside the envelope, while frozen Plan creation transports only the missing bounded `obligation_dispositions`; Plan id, Requirement id, scope, source revision, steps and relation remain native stable arguments. Unknown operations/fields and conflicting native inputs fail closed, and both paths dispatch into the same canonical Requirement/Plan admission and Plan obligation-continuity authorities. Existing one-off field carrier `plan.obligations.v1` remains bounded migration debt for already deployed frozen clients, not a second Plan authority. No compatibility decoder owns semantic decisions or persistence. The generic envelope is removed once supported clients provide guaranteed schema/version negotiation rather than per-conversation frozen snapshots; until then new schema gaps must extend the allowlisted generic transport instead of minting one bespoke lifecycle/persistence path per field.
- Exact lexical search remains necessary for dynamic registrations, manifests, string capability IDs, persisted aliases, and unrelated same-name implementations, but it is a discovery/fallback mechanism rather than the proof of static symbol completeness.
- The lexical owner is the existing `ripgrepCandidateLines` path over already policy-authorized candidates. Discovery relevance is ranked from the same full match set before its target-file budget is applied; reaching that budget remains an explicit truncation signal, not proof of semantic completeness. It consumes ripgrep's bounded `--json` match-event protocol, validates event type, authorized path, line number, and source `text`/base64 `bytes`, then redacts only retained source text. Generic process-output redaction and byte-cap markers never run before protocol validation; an over-cap capture is reported as `RIPGREP_SEARCH_OUTPUT_TRUNCATED` with the bound and a narrowing action, and malformed events as `RIPGREP_SEARCH_INVALID_OUTPUT`. Binary candidates are counted from ripgrep's structured `binary_offset` evidence and skipped without invalidating unrelated text evidence. No `--null` parser, grep fallback, or second search engine remains.

## Cognitive Plane

- Forge has one domain-independent Cognitive Plane for long-term learning and associative recall. It follows **learn early, trust gradually**, but semantic admission, abstraction and scope are model decisions: Forge must not convert repetition counts, kinds, keywords, confidence thresholds, failures or execution codes into a rule for what deserves learning or when knowledge becomes cross-project.
- `MemoryUnit` / `MemoryEdge` / `LearningSignal` are advisory knowledge contracts, never Work/Controller/Scheduler authority. `LearningSignal.kind` is open descriptive vocabulary. A model may emit no learning or many semantic deltas; per-call item/byte limits are transport/resource envelopes and larger semantic deltas are recorded in additional batches. Forge derives provenance and persists through `CognitiveWriteAuthorityPort`; Cognition cannot terminalize Work, weaken safety or create a parallel lifecycle.
- Canonical cognition metadata/relations/evidence share the Controller SQLite authority. Large immutable payloads may use SHA-256 content-addressed storage. Derived lexical/concept/graph/usage projections are rebuildable accelerators and cannot become competing durable truths.
- Existing `ExperienceRecord` remains a migration-compatible canonical record and is projected transiently into cognition during recall rather than durably duplicated. New generic memories use the cognition application service. When a deterministic `forge-incident-repair:*` Work closes a ControllerRound with current passed verification receipts, the same round-close learning composition records one evidence-backed `OutcomeObservation`, one durable repair `ExperienceRecord`, and one Cognitive `MemoryUnit` with exact source Work/Round provenance. This projection describes the verified repair candidate only; it is advisory and cannot change Work acceptance, mandatory checks, approval, ReleaseSession, Runtime cutover, or known-good authority.
- Every meaningful task start/resumption uses one bounded advisory resolver: ordinary `rh_context` work, ControllerRound composition, Workflow Supervisor turns, and Codex/Claude thin-launcher prompts share the same activation semantics. Work/Requirement/Project/Workspace candidates compete in one relevance ranking; narrower scope is a modest prior, never a Workspace starvation rule. Exact concepts expose rebuildable lexical parts, so multi-cue natural language can qualify a long memory without lowering the global cue floor. There is no internal embedding provider, semantic model or vector authority. ChatGPT may pass up to three explicitly model-authored equivalent `rh_context.recall_query_variants` (including translations) into the same bounded lexical activation; each query retains its own associative-cue floor and retrieved memories are deduplicated by their canonical address. Forge neither generates these variants nor claims cross-language recall without them. Consolidated memory and retained `derived_from` sources consume one ordinary recall slot, while conflict/supersession views remain visible. The returned `ActivationPack` is an initial working set, not semantic completeness.
- Every Controller MCP tool shares one optional bounded cognition-settlement transport field, so ordinary repository/edit/process outcomes can learn too; the model emits it only at a meaningful successful outcome boundary, not on routine micro-steps. Forge settles it after the primary operation succeeds, derives repository/session/time and optional selected Work/Requirement provenance, validates reachable scope/evidence, and invokes the existing Cognitive writer/usage writer. A settlement defect is visible advisory metadata/warning and cannot convert an already-applied primary effect into retry authority. `rh_work learning_record` remains a compatibility surface over the same writer. This adds no Reflection/Memory lifecycle, per-tool reflection ritual, or second durable authority.
- Consolidation may mechanically coalesce related traceable memories while retaining source provenance, but it does not author a more abstract lesson or promote scope. Project-to-Workspace generalization is explicit model-authored semantics: the model may use repeated independent evidence as justification, but Forge has no fixed corroboration count or source-category gate. Workspace writes require explicit portable intent and remain advisory; they never create policy authority.
- `assistant_context_usage` remains canonical ControllerRound evidence. Used/rejected feedback affects retrieval applicability, not truth confidence; stale/contradicted rejection adds explainable conflict pressure without silently deleting memory. `rh_context search` exposes bounded read-only `knowledge_*` audit over reachable Project/Workspace/Work scopes, including provenance, relations, usage and activation reasons, but audit never contributes to source mutation readiness.
- Hot/warm/cold are retrieval/retention hints, not independent stores. Machine-native encodings remain internal implementation details; MCP/ChatGPT projection is semantic typed JSON/text. See [`decisions/20260917-cognitive-memory-foundation.md`](decisions/20260917-cognitive-memory-foundation.md).

## Execution lanes

### Semantic classification authority

Execution placement, lifecycle, retry, authorization, and acceptance decisions consume typed domain contracts after ingress normalization. Human-readable ids, descriptions, prompts, log text, and error messages are evidence or presentation, not machine authority. When a legacy transport can provide only strings, one bounded compatibility ingress may normalize an explicitly constrained code/token into typed state with provenance; downstream routers and domain services must consume that typed state rather than repeat regex or substring inference. Compatibility decoders never become persistence or semantic owners.

### Failure contract authority

Machine-visible failures have a stable code plus an explicit class and retry disposition; transport projections such as HTTP status derive from that contract. Free-form messages exist for diagnostics and user presentation. A producer-specific adapter may translate a native SDK/OS error into the failure contract once, but retry policy must not be inferred from words such as `temporary`, `worker`, or `network`, and authorization must not be inferred from arbitrary prose. Ambiguous non-idempotent outcomes use an explicit reconciliation-before-retry disposition rather than generic transient retry.

### Shared live-device validation admission (Forge #192)

First-party iOS build/test commands use at most two compiler jobs, tests remain serial unless explicitly requested and opt-in XCTest workers are capped at two. Long builds use the existing asynchronous bounded child supervisor, which owns process-group timeout/signal/residual cleanup and preserves unrelated processes; build/test/smoke callers await the result. These limits do not constrain commands launched outside Forge.

`Process Runtime` owns the execution receipt and the existing global execution-Lease store owns the host resource identity: `host-service:ios-simulator-test` for iOS and `host-service:android-emulator-test` for Android. Registered simulator checks, persisted Edit/Work verification, and compatible repository commands use this one admission path. Source-only builds and static checks do not consume a device claim. These are host-wide resource classes, not new simulator instances or per-session queues; platform checks may overlap each other but not another check on the same platform.

When a claimed device is occupied, the check returns the same tracked Process handle in `starting`/resource-wait state and the original Runtime continuation retries lease acquisition. There is no 30-second admission cap: live-device checks default to a two-hour queue budget, explicit callers can select up to 24 hours, and the command execution timeout starts after acquisition. Cancellation, an expired queue budget, or checkout HEAD drift must fail before OS spawn, preserving the original Process/evidence identity. Repo-local OS locks remain defensive protection for legacy executors outside Forge; they are not a second semantic progress store. In-memory pre-spawn waiters are **not** yet restart-surviving: a Runtime restart can reconcile them as abandoned rather than resuming automatically. Do not claim crash-resilient queue acceptance without a separate real recovery proof.

### Persistent service identity authority

Recovery tool isolation and its internal wire contract are specified in [Bounded Recovery tool execution](decisions/20261103-recovery-bounded-tools.md).

Forge core persistent service ownership is machine-enumerable in `src/runtime/platform/service-inventory.ts`. The inventory owns exact current Runtime/Connector/Recovery identities and an explicit exact retired set; platform service managers own only launchd/systemd mechanics. Standalone Recovery runs MCP tools in short-lived children of the same attested Recovery release, extending its existing bounded-child JSON execution boundary. One heavy tool and two status/history reads may run concurrently; saturation fails before starting an operation. Status children have a 10-second wall bound; heavy children have a 15-minute bound and 1 MiB output bound. The HTTP/MCP gateway never executes these potentially synchronous tool implementations inline. A child observation failure is outcome-unknown, never automatic mutation replay; original operation locks, journals, request identity and CAS fences still own recovery effects. Standalone Recovery is one fault-domain-independent persistent service: its HTTP/MCP provider surface and watchdog policy share one process/lifecycle owner, while launchd/systemd supervises process death. Bounded read-only helper children, such as the known-good CPU sampler, may execute from the same immutable Recovery release but never become persistent service, mutation, or lifecycle authority. Historical Recovery Gateway/Watchdog service labels are retired migration identities, not current owners. Upgrade reconciliation may retire only exact entries from the retired Forge-core set and must verify service plus installed artifact absence. Broad `com.moretea.*` / `com.moretea.forge.*` prefix retirement is forbidden. Provider-owned services such as Desktop Operator and user-configured tunnel services remain outside Forge core retirement authority even when their labels share Forge naming.

### Tool Contract ABI authority

The published tool contract is a transport ABI, not a second semantic authority. Current and frozen clients must enter the same canonical typed handlers. The stable `rh_work` operation registry is one ABI authority shared by MCP schema generation and server-side `SuggestedNextAction` admission, so lifecycle projection cannot invent an operation the published contract does not expose or reject an operation the schema already owns. New frozen `rh_work` compatibility travels through the versioned `semantic.v1` envelope; older ad-hoc `capability_id` prefixes are shrinking migration debt and new prefixes are rejected by the runtime architecture gate.

A bridge may derive only required machine identity or CAS expectations that the target authority itself exposes through a typed status contract. Explicit caller expectations are never overwritten, partial caller-owned machine identity is rejected rather than mixed with server-derived identity, and an upgraded tool whose required fields cannot be represented fails before mutation with `RECOVERY_TOOL_SCHEMA_UNREPRESENTABLE`. Tool-surface or installed-runtime skew must remain an explicit stale/coherence condition; it must not masquerade as a missing plugin, missing user input, or authorization decision.

### Root-cause repair workflow

Repeated defects in routing, lifecycle, retry, authorization, schema compatibility, state projection, or placement are treated as architecture signals rather than isolated bug tickets. The required repair sequence is:

1. Reproduce the smallest failing behavior and name the exact machine decision that was wrong. Do not start by adding a special case for the observed string, tool name, check id, error message, or status.
2. Identify the current semantic owner and all inputs that influence that decision. Human-readable text, legacy status projections, transport session identity, and adapter-local inference are suspect whenever typed domain state already exists.
3. Search the repository for the same semantic decision and equivalent heuristics. Same-root symptoms are consolidated under one repair Work/issue; they are not fixed as independent patches merely because they surfaced through different tools.
4. Establish or select one typed owner for the decision. Adapters may normalize bounded legacy transport data once with provenance, but they do not own lifecycle, persistence, routing, retry, or acceptance semantics. Compatibility code must re-enter the canonical owner rather than create a parallel path.
5. Migrate the highest-risk consumers first, preserving only bounded ingress compatibility that cannot yet be removed. Any compatibility debt must be visible and mechanically enumerable.
6. Add focused behavioral regression for the old failure mode and an architecture guardrail when the defect class can recur mechanically. The regression must prove that the former heuristic no longer gains authority, not merely that the current example happens to pass.
7. Run one representative end-to-end journey before closing the root issue family. Related issues close only after the canonical owner is in use, dominant consumers have migrated, the guardrail passes, and any tracked compatibility debt has shrunk or has an explicit remaining owner.

Recurring infrastructure failures use one incident-repair authority. MCP failures and Scheduler progression/release/maintenance observations are normalized to a stable root code, recorded only as bounded evidence in the existing audit/event ledgers, and promoted after the existing recurrence threshold into one request-id-deduplicated system repair Work. Repeated observations append evidence to that Work; unrelated root codes remain separate; a terminal repair may create only the next generation for the same root. The repair Work still enters normal Work admission, approval, verification, Controller, ReleaseSession, and Runtime fencing. Event ledgers are evidence, never a second failure or Work state machine. Provider authorization, user-action waits, and outcome-unknown effects are excluded from automatic repair promotion.

The runtime architecture gate maintains an AST-derived semantic-string debt ledger for authority-critical code. New human-readable string matching in machine-decision branches must not be normalized by casually extending that ledger; ledger additions are architecture exceptions requiring explicit review and a migration rationale. Ordinary repair work may only remove entries. This guardrail intentionally does not ban parsers, regexes, or string matching globally: discovery, presentation, input validation, and bounded compatibility ingress remain valid when they do not become downstream semantic authority.

### Ephemeral Direct — default

Ordinary local reads, Git inspection, edits, local scripts, builds, and short checks should execute with minimal controller overhead. No persistent Work is created merely because the task is complex or investigative.

### Lightweight Managed

Commands that outlive the interactive admission window may expose an in-memory/lightweight process handle with bounded logs and wait/cancel/status. This lane does not require durable Process records, recovery membership, or Lease ownership merely to remain queryable during the current Runtime lifetime.

### Durable Workflow / Process

Persistent Work/Process state is reserved for actual continuity requirements: scheduled workflows, multi-session continuation, independent deliverables, explicit recoverability, long asynchronous workflows, release boundaries, or multi-controller coordination.

### External effects

Retired Agent Run creation/retry/acceptance and request-index code, together with Local Bridge Job submission/execution shims, have no surviving production callers and are removed rather than retained as exported APIs. The same confirmed-retired launch path no longer retains workspace launch locks, automatic worktree creation, task prompt assembly, execution-mode selection or launch-only repo identity fallbacks; the independent historical Run read, cancellation, reconciliation and cleanup paths remain. Local Bridge legacy Issue/Task/currentIssue HTTP mutations now return an unconditional 410 retirement payload even for un-migrated repositories; only historical read projections remain, with canonical Requirement/Plan/Work as the write authority. The underlying Legacy Issue cutover resolves registered checkout identity from Repository Registry before reading its SQLite migration marker; deleting, corrupting or spoofing the repository-local identity projection cannot revive a migrated writer. Unregistered legacy fixture repositories may still resolve their historical identity until registered. Unreferenced legacy Issue plan/append/split/supersede and Task-to-Work mutation exports are deleted after independent full-tree text search and TypeScript Language Service reference verification; still-live Issue/Task integrations and historical projections remain bounded by the original migration guard. This retirement uses the existing read-only rh_context TypeScript navigation sidecar and no additional local model or index daemon. Historical Agent Run/Local Bridge receipt, cancellation, HTTP 410 and release-diagnostic readback remain available; new execution enters the existing Work/Process and Thin Launcher authorities. The existing Mobile Intent plugin discovery reads both repository and controller scopes from that same plugin store (no second adapter registry or provider).

Canonical authorization grants use the one Controller Home authority. An absent persisted risk ceiling grants at most read-only access; missing owner identity does not match a requested owner; queries without any principal or owner are not authorization requests; target- or scope-restricted grants cannot satisfy unscoped or explicitly empty-scope queries. Revocation requires the same exact owner match when the caller specifies an owner. Historical v1 records remain inspectable without receiving expanded authority.

Remote or non-idempotent effects are explicit boundaries. Mail MIME header fields reject control characters before encoding, and a provider idempotency key must preserve the identity of the complete request rather than silently truncate distinguishing suffixes. Ambiguous outcomes are reported as `outcome_unknown`; Forge must not silently replay a non-idempotent remote operation.
The low-level repository command facade classifies these operations as `durable` but does not dispatch them: it returns `not_started` with `never_auto_retry`. A typed provider action or explicitly owned Durable Workflow must perform the effect and reconcile remote state before any retry after an ambiguous result.
Effectful plugin/provider actions follow the same continuity rule. Before provider dispatch, Forge binds the stable `request_id` to one durable Process identity; the MCP/ChatGPT stream is only an observation channel. Read-only actions and explicitly `direct_non_persistent` actions may remain direct, but every other effectful plugin action executes through the managed Process sidecar. Interactive timeout, stream interruption, MCP session replacement, or Runtime rotation must reattach to the same Process/receipt and must never reacquire the provider resource for a duplicate dispatch. `apply_mode=async` requests zero interactive wait and returns the durable Process/result reference immediately. A terminal sidecar writes the authoritative plugin receipt, after which repeating the same `request_id` deterministically reads/binds that receipt without replay. Before reserving a new managed Process request ID, plugin action application reuses the canonical Work-binding validator from the plugin store: only a `remote_effect` Work may bind a remote-write receipt; an ordinary `investigation` Work calls the plugin without `work_id`. Invalid bindings fail before consuming the date-scoped idempotency key; existing receipts still follow their original reconciliation. This introduces no second authority or provider.

## Requirement, Plan, and historical Work

Requirement is the canonical model-authored semantic outcome/progress aggregate. Plan is an optional revisioned planning aggregate and may reference source/Requirement provenance, but Plan approval, steps or staleness never authorize repository execution.

Historical Work is compatibility evidence only. Its old objective, relations, semantic state, completion receipts and WorkHandle records remain queryable so migrations, audits and historical Issue links do not lose provenance. No current caller may use Work to create execution placement, serialize a repository writer, bind a provider/session, drive a Schedule, close a Requirement, or infer that source/release/user acceptance is complete.

### Engineering workloop authority

Engineering profiles, Product DoD, Context Closure, design decisions, critique, semantic-tool evidence, checks and journeys are optional evidence selected by the model/project. They never admit or deny a repository mutation by themselves. Security/access, destructive authorization, secret handling, dirty ownership, Git CAS, resource fencing, exact external-effect identity and provider authorization remain mechanical gates.

### Explicit continuation and scheduling boundary

Cross-turn continuation is not a hidden Forge lifecycle. A user/model explicitly launches a session when another model turn is required. Schedule may execute one independently authorized action per occurrence. Retired autonomous continuation records are preserved only as history and are disabled on evaluation; Local Bridge and scheduler facades must not expose resume/run paths for Work-bound schedules.

## State ownership

- **Requirement** owns semantic outcome, acceptance criteria, explicit state and progress fields.
- **Plan** owns optional model-authored planning content and revision/provenance.
- **Git + Checkout Registry** own repository source, branch/HEAD/worktree placement and registered checkout identity.
- **EditSession** owns one local patch transaction, bounded path scope and after-image continuity.
- **Process Runtime** owns command/process execution identity, attachment and terminal result.
- **Resource Lease** owns physical conflict admission; it protects resources, not semantic truth.
- **Check receipts** own validation evidence for exact source/input identity.
- **Schedule** owns trigger policy, occurrence identity, bounded admission and the result of its one explicit action.
- **External effect/request ledger** owns exactly-once/reconciliation facts for replay-sensitive provider mutations.
- **Computer/Browser/provider stores** own their exact session/target/authentication facts.
- **RuntimeReleaseAuthority / ReleaseSession / Recovery** own their respective immutable release pointer, incompatible-migration transaction, and recovery transition facts.
- **Historical Work / WorkHandle / retired Supervisor records** are read-only audit and migration provenance. They own no current lifecycle, writer, checkout, process, schedule, provider turn, completion or delivery veto.

A projection, UI model, status snapshot, compatibility record or historical row may summarize these facts but cannot write a competing state. When a legacy record conflicts with a current owner, current owner/CAS/effect evidence decides; legacy data may only make destructive cleanup more conservative when bytes cannot otherwise be proven safe.

## Kernel V2 module and migration contract

Kernel V2 converges Forge toward a domain-first modular monolith. Directory placement encodes dependency direction and semantic ownership.

```text
apps / composition roots
        |
        v
adapters / providers --------> protocols
        |                         ^
        v                         |
packages/kernel/* ----------> public ports/contracts
packages/plugin-runtime/* --> neutral plugin/provider contracts
```

Current mutable domains expose one intentional public API and do not deep-import sibling persistence internals. Scheduler owns Schedule facts; Identity/Resources own portable identity and physical resource facts; Execution/Process owns command execution facts. Requirement and Plan keep their existing semantic stores and expected-revision CAS.

`packages/kernel/work` is a historical read/query compatibility package. It may normalize legacy Work rows for reads and migration evidence, but it exposes no current Work lifecycle writer and cannot be used to create placement, ownership, scheduling, delivery, completion or recovery authority. New code must not add mutable Work operations back through a different package or adapter.

### Single-authority rule

For each durable fact or lifecycle transition there is exactly one mutable authority. A projection, cache, transport session, compatibility record, provider live handle, UI model, or diagnostic snapshot may derive from that authority but must not independently decide or persist competing state. When two implementations appear to own the same semantic transition, Kernel V2 resolves the duplication by choosing one owner and deleting/merging the other rather than synchronizing two authorities.

### Migration-debt lifecycle

Compatibility exists to move consumers to the new owner, not to preserve old architecture indefinitely. Every retained compatibility shim, legacy import allowlist, translation layer, or migration-only assertion must identify: the replacement owner, the bounded legacy consumers, and a machine-observable removal condition. New production consumers of a deprecated owner are forbidden. Once the final consumer is gone or the removal condition is met, the compatibility code and its gate/allowlist entry are removed in the same coherent slice.

A fallback must never become a second semantic authority. Capability negotiation may select an explicitly supported provider/version, and safety boundaries may refuse unsafe or ambiguous execution, but missing architecture capability is repaired at the owning general layer rather than hidden behind silent fallback, duplicate persistence, or an alternate lifecycle path.

### Architecture enforcement hierarchy

Architecture checks should prove the invariant at the highest semantic level available:

1. compiler/type contracts and package/public-API visibility;
2. AST/import/dependency-graph direction and cycle checks;
3. focused semantic contract tests for behavior that static structure cannot express;
4. path existence/removal checks for finite migrations;
5. raw source-text/regex assertions only as temporary migration fences when no stronger representation exists.

Source-line-count limits are review heuristics, not architecture truth, and must not be permanent merge gates. Text assertions that merely require a spelling or forbid a provider name should be replaced by typed contracts or structural dependency checks as the migrated owner stabilizes. Architecture debt checks are shrinking ledgers: a retired dependency causes its allowlist/assertion to be deleted, never preserved for historical symmetry.

### Kernel V2 delivery cadence

Within one migration slice, gather facts in batches, decide ownership once, implement a coherent patch, then review the whole slice for authority/dependency drift before running focused checks. Repeated full-suite validation after each small move is discouraged because it slows structural work without increasing semantic confidence. Milestone/candidate boundaries receive broader cross-module review, multi-review where useful, and whole-candidate validation. Runtime baseline activation is deliberately later than source integration: a locally passing partial slice does not become the active baseline until the integrated candidate satisfies the Kernel V2 architecture contract.

Validation scheduling is derived from each check's concrete resource effects, not from a blanket assumption that every analysis gate writes the workspace or shared build cache. Proven source-read-only/no-emit checks declare reads (plus only the Git/temp/host resources they actually use) so resource-compatible gates may share one validation wave; missing or unknown effect metadata remains conservative. This projection never weakens the underlying lease conflict rules or creates a second scheduling authority.

## Runtime and MCP boundary

- Canonical Runtime is activated as one immutable whole release with a previous release retained for rollback.
- A compiled `standalone-binary` release has a closed manifest-owned execution surface: the long-lived Runtime bundle, its exact release-owned Bun interpreter, Process Runner, Check Runner, Scheduler Worker, and periodic cleanup are immutable artifacts with identities and release canaries. The signed compiled `forge-runtime` entrypoint is a supervision/identity boundary, not the long-lived JS VM. Runtime execution never resolves Bun from Homebrew, `~/.bun`, PATH, an ambient checkout, or Bun virtual `import.meta.url`; scheduler/cleanup source entrypoints remain development/source-backed mechanisms only. The single release-canary authority executes each manifest-attested entrypoint according to its artifact contract: standalone executables and non-Bun shebangs run directly, Bun shebang/source scripts use the explicitly resolved Bun runtime, and package Process Runner/Check Runner wrappers delegate the canary to their attested child rather than short-circuiting it. Every publication path runs that canary before known-good release publication.
- Canonical Scheduler idle execution is event/deadline driven, not a generic control-plane poll loop. Execution-job/lease/policy mutations and terminal Check Process persistence advance the existing `wake-signal.json` notification revision and wake immediately; lifecycle truth remains in the existing Job, Process, and Work stores, and sibling scheduler health-state writes are not wake events. With no active execution, the loop does not run a full control-plane tick merely to satisfy the five-second reconciliation cadence; it waits for an authoritative mutation notification or the 30-second schedule-admission deadline, while coarse wake polling exists only as lost-filesystem-event protection. Five-second reconciliation still runs whenever active/event-driven ticks occur. Heartbeat persistence remains health/readiness evidence and must not become scheduler work-admission authority.
- Runtime availability/recovery keeps Forge itself healthy; it does not imply exactly-once crash recovery for every local shell command.
- Controller MCP exposes **one complete tools/list inventory** assembled from the registered runtime and domain definitions. There is no `facade`/`core`/`advanced`/`full` exposure configuration; the small preferred-name catalog is routing guidance, not an alternate schema.
- The 155-tool historical inventory is the initial migration baseline, not a target count or permanent compatibility layer. Migrate equivalent callers to canonical typed executors and remove redundant public handlers and schemas rather than introducing a hidden mode. Access grants remain independent of discovery.
- Current schemas/handlers should live with their owning module. Legacy compatibility may delegate but must not independently own current business rules. Shared transport contracts and tool definitions belong in neutral contract/definition modules so the dependency direction remains transport -> application/domain authority rather than transport implementations importing one another.
- MCP tool schemas may remain frozen for the lifetime of an already-open host conversation even when Runtime reconnects onto a newer release. A versioned frozen-session wire decoder may therefore translate only explicitly bounded historical carriers into the current semantic/controller API; it owns no lifecycle or persistence, may not restore retired verify/review/finalize/ControllerRound operations, and must preserve current CAS/authority checks. The pre-Thin `semantic.v1` and current-conversation enrollment carriers are such a migration decoder. Retire that decoder only after the minimum supported MCP client contract no longer advertises those carriers and release reconnect canaries prove no supported frozen-session consumer remains.
- Work-attributed verification is an application service, not an MCP/Local Bridge implementation detail: all Work verification resolves the Work checkout/check registry, first reuses an exact-current authoritative pass/fail receipt or reconciles an already-terminal Work-bound Process with the same verification fingerprint, and only then runs a new Process when no current authority exists. Terminal receipt identity and Work evidence remain centralized in `work-verification-service.ts`; repeated verify calls for an unchanged candidate do not re-execute the check.
- WorkHandle placement recovery uses `semanticState` as the sole Work lifecycle/terminality authority. `completionOutcome` and `completionReceipt` are evidence, not independent terminal gates; an open Work may recover its exact placement only after the existing checkout ownership, source-preservation, and previous/candidate SHA CAS proofs pass.
- First-party external providers have one desired-contract reconciliation boundary: Controller plugin registry/manifest sync reconstructs the current Forge-owned permissions/capabilities/actions from source while preserving installed provider identity, transport target, lifecycle identity, provider/protocol version and enabled state. The canonical external-registration store remains the only fingerprint/revision persistence authority; manifest reads/execution never create a second registration authority or silently mutate durable state.
- User plugin installation, enablement, connection configuration and reusable authorization are ForgeInstance/Controller-global facts. Repository identity may attribute Work, fence repository resources, or appear as a typed action argument, but it cannot select a second Gmail/Google/Resend/Browser/App Store Connect manifest, config writer, or Grant domain. One-way migration admits only an unambiguous legacy value; conflicting Browser/App Store Connect identities remain preserved and require explicit resolution.
- Product bootstrap has one instance-level desired/observed lifecycle authority behind the Bootstrap Control API. CLI setup, Local Bridge readiness, packaged Runtime install/upgrade/repair projection, and doctor observation consume that same authority rather than persisting parallel setup state. Browser/tunnel/provider implementations remain adapters beneath this API.
- WSL ChatGPT browser bootstrap may create only a dedicated Forge-controlled Chromium profile when the runtime explicitly supports unpacked-extension startup. Ordinary user Chrome profiles are observational/existing-capability surfaces only; unsupported automatic extension loading must fail closed with a resumable user action.
- Workspace and Project are portable semantic identities, not aliases for Repository or checkout placement. Cross-node sync may transfer only bounded revisioned semantic projections for Workspace/Project/Requirement/Plan/Work; destination nodes persist imported facts as semantic replicas and never acquire source-node SQLite state, leases, controller/browser sessions, check receipts, raw logs, secrets, or execution placement. Import uses optimistic revision checks and fails atomically on local semantic-authority conflict.
- The structured Context Plane is advisory runtime state, not Kernel authority. Typed preference/policy/procedure/capability-intent/credential-reference records are scoped, provenance-bearing and budgeted; resolver output may influence deterministic provider preference only where the current request did not specify one. AGENTS.md remains the stable repository constitution, dynamic context is rendered on demand, raw credential material is forbidden, and loss/corruption of Context records must degrade to default routing without mutating Requirement/Plan/Work/approval authority.
- Host/platform discovery is an adapter concern, never product identity. User/profile roots, executable locations, browser products, drive mounts, service-manager availability, and Recovery deployment locations are discovered or explicitly bound; static known paths are bounded fallbacks only and may not encode a developer username, one WSL mount root, or one browser installation as semantic authority.
- Runtime and Connector persistence consume a typed platform `ServiceManagerHost`. `launchd`, `systemd-user`, and portable-session mechanics live behind that host boundary; Runtime composition does not import OS service implementations to decide product semantics.
- A materialized package Runtime is Controller-Home/release scoped and does not require a fake repository root. Repository overlay remains optional and is required only for development/repository-scoped surfaces that actually need repository semantics. Controller-scoped Browser/plugin execution likewise uses controller scope directly rather than manufacturing a repository record.
- The documented Node package runtime is a first-class product path. Normal package/bootstrap/Browser execution may not depend on unguarded Bun-only runtime APIs; executable prerequisites resolve through typed discovery with explicit missing/unsupported recovery. Plugin catalog trust is policy data: first-party allowlists are packaged/configurable policy and non-first-party providers require explicit Controller-Home trust rather than source edits.

### Controller facade and handoff boundary

- The stable Controller-facing facade is `rh_access`, `rh_status`, `rh_inbox`, `rh_context`, and `rh_work`. Internal repository, controller, evidence, maintenance, and plugin capabilities may grow behind the capability registry without creating another top-level tool for each feature.
- Handoff Inbox state is durable decision state for blocked or review-needed Controller judgement. It is not a log sink and must not become a second Requirement, Plan, Work, or Process lifecycle.
- Facade results are bounded summaries plus evidence references. Forge may report policy, verification, lifecycle, and capability facts; semantic acceptance and the decision to continue remain Controller-owned.

### Host hook boundary

Host hook files are integration surfaces, not lifecycle or architecture authorities. Forge-managed entries are identified so install/uninstall can change only Forge-owned entries while preserving sibling user hooks; legacy adapter entries are migration input rather than a second current identity. The hot host path converges on the minimal `forge-hook` entrypoint and current hook runtime, and CLI absence fails safely instead of turning a host hook into a repository failure. Setup/readiness flows may inspect and report host gaps but must not silently treat user-owned host configuration as current architecture state.

## Engineering Workloop boundary

Engineering evidence is optional model/project context layered over Requirement/Plan and exact source facts; it is not a lifecycle or admission plane. Forge owns durable facts, execution capabilities, resource fencing, source identity, verification receipts and recovery mechanics. The model owns requirement interpretation, product/architecture decisions, root-cause judgment, verification/review strategy and semantic completion.

`EngineeringWorkProfile` is a legacy type name for generic method/risk guidance; it must not create or require semantic Work. `.forge/project-engineering.json` is the source-controlled ProjectEngineeringContract and may name authority files, UX/performance/non-regression constraints, checks/journeys, platform/tooling requirements, Skill references/bindings and project exceptions.

Context Closure is derived evidence from `rh_context`, not another context database or writer. It binds the exact source revision to current source/test paths, dirty checkout context, applicable repository guidance, ProjectEngineeringContract provenance, detected language/platform, Skill/tool evidence and bounded related changes. Missing optional evidence may lower confidence, but does not invent a Work gate or replace Git/security/resource/effect authorization.

Product DoD, design decisions, critique, semantic navigation, validation and journey evidence may be persisted as receipts where supported, but their presence/absence never authorizes repository mutation or release.

## Provider boundary

Typed provider/plugin actions should use Forge capability/resource semantics directly instead of hiding host/browser/device operations inside arbitrary repository shell commands. Built-in providers may remain inside Forge when they are tightly coupled to Controller policy and lifecycle; independent products/providers retain independent release boundaries and integrate through the Plugin Protocol.

### Computer and macOS provider boundary

`Computer` is the user-facing interaction product boundary. Browser and Desktop remain distinct semantic subdomains inside that product: Browser owns DOM/tab/navigation/session/transaction semantics, while Desktop owns generic application observation, input, capture, and native-platform interaction. Ordinary Computer browser actions attach to existing native Chrome/Vivaldi windows and exact tabs (including background tabs); they never enter a Playwright CDP or managed/isolated-profile fallback. The independent Browser scripting provider may still run Playwright only through an explicitly selected scripted Browser route. Computer cannot create the first browser window merely because a browser process is running; a missing window fails closed instead of silently starting a new UI. An explicit existing-resource request also fails closed when no unique matching tab exists, never creating a replacement. The native Computer Browser capability is built into the first-party Forge release, registered and enabled by default in every repository; it is not installed, configured, or disabled through the independent Browser-script plugin. Its runtime readiness still depends on the target platform's native browser availability and permissions. Browser defaults attach to the existing user browser and fail closed when unavailable; legacy implicit managed-profile defaults migrate to native attach. Across multiple installed browsers, select a unique exact-URL match before any frontmost-browser preference, including on first use with an explicitly supplied but unbound session ID; same-origin presence is a profile hint, never authority to overwrite an unrelated user tab. Browser may consume provider-native support through `computer.browser_automation.v1`, but neither the internal `browser` adapter identity nor concrete provider identity such as `desktop_operator` is a second user product or routing/session authority. Internal adapters remain exactly addressable only for trusted composition and migration.

On macOS, Forge Desktop Operator is the independently released native Computer provider. Its Git repository, app bundle identity, user LaunchAgent, socket endpoint, live native handles, and TCC permissions remain provider-owned and release-independent. Its trusted registration is explicitly provider-only: normal plugin discovery exposes `computer`, while diagnostics and lifecycle composition may still address `desktop_operator` exactly. Forge owns trusted catalog selection, registration, capability/action policy, authorization, provider selection, and the `forge computer setup|status|doctor|update|uninstall` product facade. The stable Desktop Operator bundle/LaunchAgent identity must not be renamed merely to match product wording because TCC identity and provider lifecycle are intentionally independent from Forge Runtime releases. Durable application interaction-target authority is Forge-owned in Controller SQLite. Public Computer actions use a stable `target_id`; provider session/handle identities are live bindings only. Rebind, target use, and retirement serialize on the same target-scoped authority lease, and a provider restart may rebuild a binding only after the stable application identity is re-verified. Rebinding occurs before semantic dispatch; once a non-idempotent provider mutation is dispatched, an unknown transport outcome is never automatically replayed. A host application or browser discovery result is not a Computer capability proof: a capability is supported only when the current platform has a compatible provider, and it is ready only when that provider is registered, enabled, declares the capability, and has recorded healthy evidence. On an unsupported platform, status and setup fail before probing a foreign provider; Runtime must not create a legacy provider binding or retry a foreign transport.

`computer.console.unlock.v1` is a protected Computer capability, not a widening of `computer.input.v1`. Forge owns its provider-neutral contract, provider selection/negotiation, and explicit single-use authorization boundary; Desktop Operator owns macOS lock-state observation, exact `loginwindow` binding, bounded physical input, attempt limiting, and authoritative locked-to-unlocked postcondition verification. Raw macOS credentials never enter ChatGPT, MCP arguments, or Forge Runtime. The frozen 20-tool ChatGPT deployment ABI does not grow dedicated console-unlock tools: refreshed clients invoke typed `computer/console_unlock_prepare` and `computer/console_unlock` actions through the existing stable `plugin_action_execute` dispatcher. Those actions use the explicitly restricted `direct_non_persistent` lane: manifest/schema validation and per-invocation authorization still apply, but Work attribution is forbidden and the invocation bypasses plugin request indexes, receipts, Process/ExecutionJob state, evidence, and replay. While the console is unlocked, prepare asks Desktop Operator to collect the credential in a provider-local secure field and returns only a short-lived opaque single-use handle; unlock later consumes that handle while the console is locked. The old atomic `computer_console_unlock_prepare` / `computer_console_unlock` handlers remain internal-only and do not widen the stable Connector schema. Results are allowlisted projections and cannot echo credential material. Ordinary `desktop_key`, `desktop_type_text`, batch, pointer, screenshot, application activation, shell, and compatibility paths cannot target the lock screen through this capability.

Trusted `ExternalPluginRegistration` is the endpoint/lifecycle authority for an installed Computer provider. A release-independent Desktop Operator install receipt may refresh only installed release metadata when it proves the same already-trusted socket, verified LaunchAgent, exact trusted executable binding, bundle identity, and provider manifest; the receipt's own program-name hint is only self-consistency evidence, never lifecycle authority. The receipt is evidence, never a second endpoint/lifecycle authority, and contradictory matching evidence fails explicitly. Its local JSONL transport uses a platform-local endpoint (a Unix-domain socket on Unix or a Windows named pipe on Windows), not a browser-discovery proxy or a second readiness authority. A Computer provider must resolve only from a trusted `ExternalPluginRegistration`; Runtime no longer binds an unregistered Desktop Operator socket as a compatibility provider. Provider protocol negotiation prefers provider-neutral `computer_execute`; legacy `macos_browser_automation` is compatibility-only and cannot become Browser authority. Forge uninstall must complete the provider-owned native uninstall lifecycle before forgetting a registered provider, so package/registration cleanup cannot orphan a running native service.

### iOS physical-device boundary

- Physical-iPhone everyday App actions are exposed exclusively by the repository-scoped `computer` plugin's `physical_device_*` capability descriptors, dispatched by the existing `plugin_action_execute` authority. The `ios` plugin retains Xcode, Simulator and explicit agent-device/XCTest development/test actions. `computer` delegates to the existing CoreDevice executor and its exact-phone authorization, not a second transport or session writer. Physical app open reactivates the target App on both new and reused sessions (and honors explicit terminate-existing), invalidates earlier foreground observations before activation, and never infers foreground from a cached session or launch receipt. Cross-action RemoteXPC prewarm is deferred to the first input action, and validated screenshot dimensions avoid a redundant display query on observed opens. Physical app activation rejects devices that CoreDevice reports as disconnected and lock-state replies without an explicit boolean `passcodeRequired`; intent-ranked capability discovery uses live source-derived plugin manifests so persisted status projections cannot advertise retired action ownership, while discovery remains read-only. Strong-confirmed one-file App Documents exports reject basic truncated PDF/PNG/JPEG copies (and invalid HEIC first-box bounds) before atomically indexing verified framing receipts inside the same private Controller session folder; prior indexes are size-capped and validated against the exact App/session and each receipt before a subsequent phone copy, never silently overwritten when malformed; there is no separate document writer or medical inference service. Controller-scoped Computer actions do not expose repository-bound phone input.
- Exact repository-owned Computer phone action lookup, submission, post-effect manifest refresh and Work receipt preflight do not run unrelated Controller plugin migrations. Their canonical request index, receipts and `ios-physical-device`/action-local physical-device grants retain repository scope when Controller migrations later run. Exact-context receipt reads validate repository, plugin/action and index/receipt identity before reuse; mismatched or already-misclassified historical records fail closed without repair or resend. Browser/Desktop Computer migration keeps its existing Controller owner. This reuses the same manifest cache, receipt and Grant writers; no new persistent authority or cold-start lifecycle is introduced.

- `ios-device` is the single physical-device resource domain. Backend/engine details may vary, but they must not create independent mutation authority or concurrent ownership for the same phone.
- Agent-device readiness is capability-negotiated from a reviewed version/help contract and a stable contract fingerprint. A preferred version is support guidance rather than authority; unsupported or unreviewed pre-1.0 contracts fail closed instead of guessing flags or semantic support.
- Application adapters own app-specific semantic targeting and assertions; provider code owns transport, device/session lifecycle, and command execution. Semantic action failure is distinct from transport/session death, and unknown mutation outcomes are fenced rather than blindly replayed.
- iOS evidence is bounded and redacted. Read-only lifecycle/screenshot capability must never be represented as proof of semantic mutation capability. The existing CoreDevice screenshot observation authority uses a private 0700 per-session artifact directory and 0600 screenshot files, invalidates old observations before recapture, deletes partial failures, and rejects missing, oversized or malformed PNG structures (including damaged chunk CRCs) before issuing an observation ID and a SHA-256/byte-count provenance receipt; image bytes alone never certify the foreground App or displayed product price. The source-only Computer smoke verifies the observed screenshot's file SHA-256 and byte count against its CoreDevice receipt before reporting the path and observation ID, but expressly makes no SKU/price or activated-Runtime claim. Computer reports CoreDevice `observationReady` separately from pinned RemoteXPC HID `inputReady`; an unavailable or incorrectly versioned toolchain may leave screenshots usable without claiming interaction readiness. Generic Browser/Desktop Computer manifest reads never invoke synchronous HID Python probes, including when CoreDevice itself is ready: they consult only the short-lived successful probe cache. An `inputReady=false` manifest reading with an empty or stale cache is reported as unverified (passive status `probeState=unverified`) and never implies a missing toolchain; only a real failed strict probe may produce a toolchain-missing warning (#289). Explicit RemoteXPC input retains the sole strict Python package/version probe. The single Controller-owned versioned Python path is provisioned by `scripts/install-ios-hid-toolchain.sh` only with authorized host execution, and never changes the active Runtime release.

## Browser Runtime V3 contract

Browser Runtime V3 is the current Browser execution authority. Controller-home BrowserSession state is the sole durable browser-session authority; stable provider/resource identity is distinct from mutable observed URL/title, and provider-local live handles are acceleration state only. The accepted Browser Runtime V2 ADR remains historical rationale rather than a competing current authority.

Browser actions bind exactly one provider before execution, selected deterministically by the configured mode and exact target; registering multiple candidates or silently rebinding on a pre-action failure is forbidden. Attach mode uses one configured CDP endpoint or one explicit native browser product, not an ordered CDP/native/managed fallback chain. Managed Playwright requires explicit selection. Common DOM and typed browser-internal operations must remain background-safe. Native macOS sessions reuse or recover only exact Forge-owned `windowId` + `tabId` identities. Provider-wide tab inventory is an optional optimization: when the installed broker cannot enumerate tabs, Forge may create a new plugin-owned tab or validate a saved exact ref, but it must not scan for or guess an unrelated user tab.

Foreground presentation is an explicit effect reserved for capabilities that truly require physical pointer/keyboard input or human handoff. Browser `trusted_input` never silently activates a background tab or converts CSS viewport coordinates into desktop coordinates. If the native broker lacks the required trusted-input capability, Browser fails with a typed capability error; an explicitly requested Desktop Operator foreground/physical action remains a separate authority boundary. Mutating provider actions are complete only when their declared postconditions are verified; transport, Apple Events, Accessibility, socket, or CGEvent success alone is not semantic completion.

The public Browser action surface remains compatible across Playwright/CDP/native providers. Current native compatibility may omit optional broker methods such as global tab inventory while preserving exact-ref lifecycle safety. DOM automation through Chrome/Vivaldi Apple Events still requires the browser's JavaScript-from-Apple-Events permission; missing permission fails closed instead of weakening the provider contract. Browser replay safety is derived from the Browser Runtime transaction contract rather than an adapter-local action allowlist, and native session liveness/reconciliation is centralized outside the plugin composition root. A human-handoff host may persist its own InteractionSession result, but BrowserSession mutation returns to the canonical Runtime authority.

## Testing and verification

Tests are verification evidence, not an alternate architecture authority.

- Development/task gate: typecheck + static architecture + generated-authority drift + source-duplication classification + controller-UI reproduction + manifest validity + affected tests.
- Main candidate: task gate + core regression + Runtime smoke.
- Release candidate: main gate + full regression + release packaging/readiness.
- Static architecture additionally requires the production `src/**/*.ts` relative-import graph to be acyclic. Neutral contracts may break dependency direction; dynamic imports must not be used merely to conceal a static architecture cycle.
- Source-duplication governance permits only classified distribution/template projections, guidance aliases, and placeholders; unclassified exact duplicates fail the gate. Generated copies may exist for packaging, but manual implementation duplication is not an accepted source-authoring model.
- Test governance validates registration, resource classification, selection and execution isolation; it does not impose arbitrary global test-line or resource-count budgets.
- Prefer a small number of architectural invariants, focused module tests and essential integration/E2E coverage. Delete implementation-coupled or retired-compatibility tests when the underlying obligation is removed.

## Module Boundaries and Language Evolution
This policy applies to **all Forge source development**. `AGENTS.md` is the entry point. `docs/architecture/CURRENT.md` records active authorities and `docs/reference-configs/runtime-architecture-guardrails.md` defines existing correctness and release constraints. ## Architecture

**The model owns semantic decisions. Thin Forge owns capabilities, durable facts and mechanical correctness.** Preserve one repository, one Runtime release and a modular monolith. Standalone Recovery is an independent failure domain, not another Kernel. Signed OS-native services may be separate processes to preserve platform permission identity; they do not own Requirement, Plan or Work facts.

| Responsibility | Canonical source area | Ownership |
| --- | --- | --- |
| Requirement/Plan/Work | `packages/kernel/goal`, `packages/kernel/work` | stable semantic intent, plan and work |
| Controller and ChatGPT effects | `packages/kernel/controller`, `supervisor` | controller identity/round; exact-send effect authority belongs to Supervisor |
| Scheduling | `packages/kernel/scheduler` | occurrence and wake, not model workflow decisions |
| Identity/grants | `packages/kernel/identity` | principal, permission and user requests |
| Knowledge | `packages/kernel/cognition`, `packages/kernel/memory` | distinct scoped evidence and knowledge facts |
| Wire contracts | `packages/protocols` | neutral typed contract only |
| External interfaces | `adapters/**`, migrated `src/cli/**` | translate MCP/CLI/provider calls; no duplicate durable writer |
| Runtime composition/GUI | runtime composition root, `apps/**` | wire implementations and render state, not business transitions |
| Plugin mechanisms | existing plugin-runtime and Computer owner | typed actions, target binding, native provider primitives |
| Recovery | standalone Recovery authority | restore crashed canonical release, not parallel semantic state |

Domain ownership is semantic, not just folder names. New cross-domain imports must use the target `packages/kernel/<domain>/api/index`; never reach into another domain's `domain/`, `application/`, `infrastructure/` or `ports/`. Kernel must not import concrete adapters, apps, Supervisor implementations or protocol transport writers. Only composition roots select implementations.

## Mechanical enforcement

`node scripts/check-module-boundaries.mjs` uses the TypeScript AST to examine imports, exports, literal dynamic imports and CommonJS `require`. It fails for new Kernel → `adapters/`, `apps/` or `supervisor/` dependencies, private cross-domain imports, cycles between kernel domains, and unapproved Kernel → legacy `src/**` edges.

The 21 existing imports from kernel infrastructure into historical `src/**` implementations are exact migration exceptions in `docs/architecture/kernel-legacy-edge-debt.json`. This file is **shrinking debt, not an authority or a blanket allowlist**: no new exceptions, no wildcard allowances. When old callers migrate, remove their entries in the same change. A stale entry is a failing check.

The checker is one step in existing `check:task` → `check:main` → `check:release`, not an additional lifecycle or CI authority. Verify the checker itself with a negative proof (an illegal import fails) and positive proof (the real existing source passes). If new path aliases/package export mappings are introduced, update its resolution rather than leaving an unchecked way around it.

## Change discipline

1. Examine the actual source, current architecture, owner, and existing Requirement/Plan/Work first; reuse the current objective. Small edits do not require a manufactured workflow.
2. Identify the root cause and one owning domain. Prefer delete/merge/repair over a fallback, extra status, duplicate provider or new background supervisor.
3. Implement one coherent slice. Move callers and remove the legacy writer/path; synchronize public contracts, existing checks and architecture documents. Preserve other writers' dirty files.
4. Verify changed behavior, external effects, unknown-send protection, authorization and release invariants without weakening gates. Reuse unchanged validation receipts.
5. Commit only the verified slice. Integration follows existing GitHub/main protections. Source commits do not prove installed Mac/WSL Runtimes or an active-release canary.

An explicit brief ADR is required for a **new** durable writer, authority, lifecycle state, daemon, cross-process protocol, production programming language, or independent deployable. Record owner, invariants, consumer boundaries, concurrency/crash/replay/retention, migration/deletion, packaging, rollback and observable acceptance. Routine refactoring needs no ADR.

## Language strategy

TypeScript remains responsible for fast-changing orchestration, MCP, plugin contracts and integrations. Keep Swift where native macOS Accessibility, TCC or AppKit identity is required. The existing Rust/Tauri desktop shell is not a reason to translate the Kernel.

Rust is optional and **incremental**, used only after identifying a real systems-level advantage (process/resource ownership, IPC/atomicity, crash/locking or a narrow performance hot path). Start with a bounded interface and measured problem, prove Mac and Linux/WSL behavior and packaging, cut over a single owner, then delete the replaced TypeScript writer and obsolete bridge. No dual persistent stores, permanent TS/Rust fallback, new state or Rust-percent target. Go/Python do not become alternate production Kernels without a separate proven requirement.

A file over 1,000 lines merits responsibility review, not an arbitrary failing size gate. Monitor actual dependency fan-out, cycles, duplicate ownership, controller bookkeeping overhead, delivery lead time and shrinking exceptions. Improve the common structural guard rather than expanding per-incident regex rules.

### Workflow capability dependency authority (2026-10-21)

The executable Workflow step graph is the sole source for capability and reconciliation dependencies. `workflowCapabilityDependencies()` in `packages/workflow-runtime/domain/workflow-asset.ts` derives a stable, deduplicated inventory from capability steps and their `reconcileWithCapabilityId`, and first-party installation binds those capabilities rather than a second authored list. ## Acceptance-test-driven development (ATDD)

1. Before editing, state observable user goal, prior *actual* success receipt, current failing counterexample, exact source/Release/loaded worker, original effect/task owner, affected paths, side-effect budget and rollback identity. Document behavior that must not change.
2. Reproduce RED. Prefer focused deterministic fault injection for native timeout with no onDisconnect, stale response, simultaneous RPC, postMessage throw, extension reload/source-path mismatch, wrong-tab owner, foreign draft, stream interruption, and unknown Send. Label mocks separately from real results. Do not make a second real external Send to generate RED.
3. Minimal GREEN: verify targeted and pre-existing adjacent tests, especially safety (no wrong-tab or repeated Send) **and** liveness (legitimate pending effects eventually recover); review exact complete diff.
4. Fixed candidate: verify CI, ownership, test manifest and relevant gates; avoid broad refactoring during a narrow repair.
5. Real user-behavior acceptance for an automation fix: verify immutable release, **loaded** Chrome extension path/hash (not just projection), Native Host live heartbeat/claim, original pinned conversation ownership, pre-send prepare, dispatch_started→effect_applied, assistant receipt→next successor, and restart/reconnect behavior including a locked macOS console if claimed. Prove zero duplicated external side effects.
6. An independent real CONTINUE→CONTINUE→DONE canary tests the terminal protocol; original production Writer must independently demonstrate safe forward progress. DONE only for genuinely accepted delivery.

Report separate CODE, INTEGRATION, LOADED WORKER, and LIVE AUTONOMOUS LOOP verdicts: PASS, FAIL, NOT RUN, or BLOCKED, with exact evidence refs and remaining blockers. For documentation-only work a live ChatGPT Send is not needed; for a claim of restored automatic delivery, the real loop cannot be skipped.
