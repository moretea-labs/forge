# Route and Session Concurrency Baseline

Baseline date: 2026-08-09

This baseline is generated by the repository benchmark rather than hand-authored:

```sh
bun run benchmark:route-session-concurrency --iterations 7 \
  --output docs/operations/route-session-concurrency-baseline.json
```

The JSON output contains every measured phase for every scenario, p50/p95/p99, success rate, timeout rate, contention rate, failure rate, and the derived threshold. The threshold policy is:

```text
max(1 ms, observed p99 * 1.25, observed p95 * 1.5)
```

The one-millisecond floor means an unused or sub-millisecond phase still has a non-zero governance value. Thresholds are a baseline comparison signal, not a reason to add waiting or to hide contention.

## Physical concurrency and cache evidence

The benchmark now uses two temporary Git repositories plus one real `git worktree`, registered as two checkouts of the same repository. Every concurrency sample launches Process Runners and writes an ignored marker in the intended checkout; it no longer substitutes context reads or invented checkout ids for physical work.

Across seven iterations:

- two-repository concurrency: 14 logical subscribers, 14 physical executions, 14 independently verified repo identities;
- same-repository/different-checkout concurrency: 14 logical subscribers, 14 physical executions, 14 independently verified checkout identities;
- same-checkout contention: 14 logical submissions, 7 physical executions, and 7 bounded Lease conflicts; no blocked marker was written;
- Check cache: 28 logical subscribers, 14 physical executions, 7 active coalesces, 7 completed cache hits across the clean worktree, and 7 dirty-workspace invalidations.

The Check identity is repository-scoped in the durable binding and content-bound by the workspace revision, check definition digest, environment/toolchain fingerprint, timeout contract, and safe reuse scope. Dependency lockfiles and relevant repository config participate through the content revision. Session and request ids are deliberately subscriber identity, not cache-key inputs. Cross-checkout reuse is enabled only when both checkouts are clean and the check declares fingerprintable read-only effects; the dirty-workspace sample changes the content fingerprint, narrows reuse to checkout scope, and forces a new Process.

`durable_job_submit` measures durable Process admission and persistence because new ExecutionJob creation is retired. `gateway_restart_recovery` reads the persisted Process handle from a fresh store access before terminal completion.

## Required interpretation

- Same-checkout contention is successful behavior when it returns a bounded contention result. It is therefore reported with contention rate 1.0 and failure rate 0.
- Different checkouts and different repositories must retain success rate 1.0 in the baseline matrix.
- Cache accounting must retain the invariant `physicalExecutions < logicalSubscribers` only when the report also proves coalescing/reuse and explicit invalidation with distinct Process ids.
- An increase must be investigated by phase. Raising a timeout or adding a global lock is not an acceptable remediation.
- A new baseline must be generated from the benchmark on the candidate committed HEAD. Do not manually edit percentile or threshold values.
- The benchmark uses temporary controller homes and temporary Git repositories, so it does not mutate registered production repositories.

## T2 prior failure classification

The previous T2 Work failed verification before commit because its isolated worktree had not materialized Bun type dependencies. `tsc` reported `TS2688: Cannot find type definition file for 'bun'`; the fallback command also resolved dependencies during verification and changed its input state. This was an infrastructure/dependency-materialization failure, not evidence that the resolver implementation was invalid.

The corrected procedure is:

```sh
bun install --frozen-lockfile
./node_modules/.bin/tsc --noEmit
```

The frozen install prevents verification from silently changing the lockfile or selecting a different dependency graph.
