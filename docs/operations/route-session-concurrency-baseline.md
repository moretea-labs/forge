# Route and Session Concurrency Baseline

Baseline date: 2026-08-05

This baseline is generated by the repository benchmark rather than hand-authored:

```sh
bun run benchmark:route-session-concurrency --iterations 7 \
  --output docs/operations/route-session-concurrency-baseline.json
```

The JSON output contains every measured phase for every scenario, p50/p95/p99, success rate, timeout rate, contention rate, failure rate, and the derived threshold. The threshold policy is:

```text
max(1 ms, observed p99 * 1.25, observed p95 * 1.5)
```

The one-millisecond floor means an unused or sub-millisecond phase still has a non-zero governance value. Thresholds are a baseline comparison signal, not a reason to add waiting or to hide contention.

The cold-read distribution includes the initial Git/projection observation: Git observation and projection p95/p99 were 78.62 ms, with a 118 ms derived phase threshold. Warm projection p95/p99 was 0.34 ms. Requirement Board storage p95/p99 was 25.30 ms. Work prepare storage p95/p99 was 5.58 ms. Direct Edit lock wait p95/p99 was 25.73 ms. `durable_job_submit` measures durable Process admission and persistence because new ExecutionJob creation is retired. `gateway_restart_recovery` reads the persisted Process handle from a fresh store access before terminal completion.

## Required interpretation

- Same-checkout contention is successful behavior when it returns a bounded contention result. It is therefore reported with contention rate 1.0 and failure rate 0.
- Different checkouts and different repositories must retain success rate 1.0 in the baseline matrix.
- An increase must be investigated by phase. Raising a timeout or adding a global lock is not an acceptable remediation.
- A new baseline must be generated from the benchmark on the candidate committed HEAD. Do not manually edit percentile or threshold values.
- The benchmark uses temporary controller homes and temporary Git repositories, so it does not mutate registered production repositories.

## T2 prior failure classification

The previous T2 Work failed verification before commit because its isolated worktree had not materialized Bun type dependencies. `tsc` reported `TS2688: Cannot find type definition file for 'bun'`; the fallback command also resolved dependencies during verification and changed its input state. This was an infrastructure/dependency-materialization failure, not evidence that the resolver implementation was invalid.

The corrected procedure is:

```sh
bun install --frozen-lockfile
./node_modules/.bin/tsc --noEmit
```

The frozen install prevents verification from silently changing the lockfile or selecting a different dependency graph.
